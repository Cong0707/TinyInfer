# 幽灵开关：设了不生效的参数

这一类 bug 的形态都一样：**代码读了这个环境变量，但读完之后只做了无关紧要的事，
或者根本没用它做本该做的事。** 症状是「调参数没反应」，而日志和代码都看不出异常。

比「完全没人读」的开关更危险，因为它看起来是通的。

## TI_SLOTS

**声明的位置和真正生效的位置不同义。**

```
  engine.py:374   _slots = int(os.environ.get("TI_SLOTS", hw.expert_slots))
  engine.py:381   if _slots > 0: set_cache_capacity(_slots)   # 只设了 Marlin repack 缓存
  tune.py:314     env["TI_SLOTS"] = str(int(s))               # 训练器以为在扫槽位数
```

engine 读到 `TI_SLOTS` 之后，只用它调整了 Marlin 的 repack 缓存容量 ——
**专家槽位数本身仍然来自 `hw_plan.expert_slots`**，完全没被覆盖。

所以：

- 手工设 `TI_SLOTS=8` 想减少槽位 → 没反应（实测日志始终显示 `slots=24`）
- 训练器 `tune --slots` 扫一整轮 → **每一档其实都是同一个配置**，扫出来的
  「最优点」是纯噪声

这个和之前发现的两类问题同源：

1. `TI_AUTO_SLOTS` 同名不同义（engine 指专家槽位扩容、server 指并发会话数，
   默认值还相反）
2. `TI_SLAB_FRAC` 设了不生效（0.05 和 0.28 都装 10~13 层，疑有下限或计算被覆盖）

## 该怎么修（还没做）

`TI_SLOTS` 需要一个真正的覆盖点。槽位数来自 `hw_plan.expert_slots`，它在
plan 阶段就定了，而 ExpertStore 创建时直接用这个值。正确的做法是让 plan 层
接受覆盖：

```
  环境变量 > tuned.json 的 chosen.slots > 规划器算出的值
```

和 `pool_ratio` 已有的优先级一致。改之前别用 `tune --slots`，它扫的是假数据。

## 这一类问题的检查方法

**调一个参数之前，先验证它真的被读到。** 具体做法：

1. 设一个极端值（比如 0 或 1），看日志/行为有没有变化；
2. 在读取处加一行打印，确认代码走到了那个分支；
3. 看这个值最终被传给了谁 —— 如果只传给了「缓存容量」这种边缘用途，就不是
   你以为的那个开关。

第三条最关键：**同名变量在两个模块里指两件事，是这类 bug 的主要来源。**
