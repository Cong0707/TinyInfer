# 幽灵开关：一次误判，以及真正的教训

## 先说结论：TI_SLOTS 不是幽灵开关，我判错了

我一度写下「`TI_SLOTS` 只影响 Marlin 缓存、不改变专家槽位」。**这是错的。**

实测：

```
  TI_SLOTS=8     -> 实际 slots=8   (而 plan 摘要打印的是 24)
  TI_SLOTS 未设  -> 实际 slots=24
```

`engine.py:742` 的 `vram_slots=_slots if device != "cpu" else 0` 确实把覆盖后的
值传下去了。是我看走了眼 —— 我看到 374 行 `TI_SLOTS` 被 `set_cache_capacity`
用掉，就先入为主地以为它只有那个用途，然后拿日志里的 `slots=24`（那是 plan
的规划值）当证据。

**这和 `cache` 那次是同一个坑**：日志里打的是规划值，不是实际值。

## 真正的教训：日志必须区分「规划」和「实际」

今天有两次判断错误直接来自这一点：

1. `cache=15.93GB` 显示的是 `plan.cache_gb`，实际只分配到 0.53GB（28 个槽位）；
2. `slots=24` 显示的是 `plan.expert_slots`，实际设 `TI_SLOTS=8` 后是 8。

两次我都先看到「值没变」就下结论说开关是死的。**规划值是设计意图，实际值是
运行结果，两者可以差几十倍，而日志只打了前者。**

正确的做法是在实际分配处加一行「规划 -> 实际」的对比打印（`cache` 那处已经
加了）。判一个开关是否生效，也不能看日志，要看**运行时对象的属性**：

```python
  eng.expert_store.slots.slots          # 槽位真实值
  eng.expert_store.ram.capacity_entries  # 缓存真实容量
```

## 仍然可疑的

`TI_SLAB_FRAC`：设 0.05 和 0.28 都只装到 10~13 层，看起来有下限或者被后续计算
覆盖。但这次我没做同样的属性级验证就下结论 —— **在验证之前，它只能算「未确认」，
不能算「不生效」**。上一个误判就是证据。

## 这一类问题的正确检查方法

1. **设一个极端值（0 或 1），读运行时对象的属性** —— 不要看日志，日志可能是
   规划值；
2. 在读取处加打印确认分支走到了；
3. **跟着这个值往下走**，看到它最终传给了谁。不要看到第一次使用就停下 ——
   `TI_SLOTS` 第一次出现在 `set_cache_capacity`，但真正的用途在几百行之后。

第三条是我这次犯错的原因：**一个变量可以在多处被使用，看到第一处就以为那是
全部。**
