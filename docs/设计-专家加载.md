# tinyinfer 三级存储与专家加载设计

> 范围：显存槽位、内存缓存、磁盘分片三级存储的职责划分、账目与接口契约。
> 目标硬件：RTX 5060 Laptop，8 GB 显存（sm_120）+ 47.2 GB 内存 + NVMe。
> 目标模型：DeepSeek-V4.1-Flash，HF safetensors 共 510.286 GB，直接加载，不做格式转换。
> 实现位置：`tinyinfer.loading`。
> 本文只写设计与契约。数值分为两类：**账目**（由文件 header 或规格算出的定值）与**规划取值**
> （按实测标定后选用的保守档位，不是测量记录）。文中说"约"的地方都是约数。

---

## 1. 分级职责

~~~
NVMe ── 510.3 GB HF safetensors，只读，禁止整层 mmap
  │       O_DIRECT / NO_BUFFERING 读专家 blob（每专家 2 段）
  │       4–8 线程，队列深度约 8
  ▼
RAM（47.2 GB）── 非专家全驻 + 专家缓存 + 长上下文 KV + staging
  │       pinned H2D，24 槽环形复用
  ▼
VRAM（8 GB，约 6.6 GB 可用）── 注意力常驻 + 专家槽 + 激活 / KV 窗口
~~~

设计规则：

1. **显存只放"每 token 必用且复用率高"的东西**：注意力权重（常驻越多，PCIe 流量越小）、专家槽（暂存）、激活与 KV 窗口。
2. **内存放"每 token 必用但显存放不下"的东西**：非专家权重、专家缓存、长上下文 KV、pinned staging。
3. **磁盘只承担专家与 Engram 表**：两者合计 491.5 GB，无法常驻。非专家永远不从磁盘读（17.78 GB 全驻内存）。
4. **专家槽是暂存不是缓存**：槽被换出时不丢数据（内存缓存里还有），因此显存占用可解释、可封顶。
5. **反量化在消费端**：磁盘、内存、PCIe 上永远是 18.8 MB 的原始 fp4 blob；GPU 拿到后直接喂 fp4 反量化 kernel，不生成常驻的 bf16 副本。

## 2. 磁盘布局契约

### 2.1 张量账目

按 safetensors header 解析得到的定值，不是估算。

| 类别 | 字节 | 说明 |
|---|---:|---|
| 路由专家权重（fp4 packed） | 17,694,720 B/专家 | w1 2304×2560 I8，w2 5120×1152 I8，w3 2304×2560 I8 |
| 路由专家 scale（e8m0） | 1,105,920 B/专家 | w1/w3 2304×160，w2 5120×72 |
| **单专家合计** | **18,800,640 B** | 17.93 MiB |
| 单层专家 | 7,219,445,760 B | 384 × 18.80 MB |
| 单层非专家 | 170,055,128 B | 含注意力、shared expert、HC、gate |
| 40 层专家 | 288,777,830,400 B | 288.78 GB |
| 40 层非专家 | 6,802,205,120 B | 6.80 GB |
| embedding + head | 1,323,827,200 B ×2 | [129280, 5120] bf16 |
| Engram 表单张 | 101,377,628,352 B | 98.306 GB fp8 权重 + 3.072 GB e8m0 scale（[rows, 8]） |
| Engram 表两张 | 202,755,256,704 B | 2 × 101.378 GB |
| Engram 投影（wkv + q/k） | 314,880,000 B | 2 层，wkv 25600×6144 fp8 |
| MTP/DSpark 3 层 | 约 8.0 GB | 由总量反推，约 2.67 GB/层 |
| vision | 0.971 GB | 可禁用 |
| **总计** | **510,286,023,000 B** | 510.286 GB |

存储形状与逻辑形状的关系：权重张量是 packed 存储，**列数为逻辑输入维的一半**（每字节装 2 个 fp4 nibble）；scale 张量的列数为逻辑输入维的 1/32。例如 w1 存成 [2304, 2560]，逻辑上是 2304×5120。

### 2.2 专家在文件里的物理排布

- 张量在文件内按**字典序**排列（0, 1, 10, 100, …），不是按层号或专家号连续。
- 单个专家的 3 个 weight 相邻（共 17.7 MB 一段），3 个 scale 相邻（1.1 MB 一段），**两段之间隔得很远**。
- 因此**不存在"每层一个 7.22 GB 大 blob 可顺序读"**这种布局。读取器必须按 (shard, offset) 聚合，不能假设单个专家在文件中连续。
- 读取粒度由此确定：**每专家 2 段，每 token 240 个专家 = 480 次 pread**。

### 2.3 全程保持 fp4 packed

权重在磁盘、内存、PCIe 上永远是 packed uint8（0.5 B/参数），反量化只发生在 GPU 消费端。任何"先反量化成 bf16 再缓存"的做法（bf16 为 70.8 MB/专家）会让内存需求涨到 3.8 倍，**不允许**。

## 3. 每 token 的 I/O 账目

### 3.1 冷读总量

| 项 | 冷缓存 | 说明 |
|---|---:|---|
| 专家数据 | 4.512 GB | 240 × 18.80 MB = 4,512,153,600 B |
| 专家读取次数 | 480 pread | 每专家 2 段；按 offset 排序后 4–8 线程并行 |
| Engram 行 | 12,288 B | 2 层 × 24 行 × 256 B；4 KB 页粒度下折算 ≤196,608 B/token |
| 非专家流（未常驻的注意力层） | 0–1.36 GB | 常驻 34 层时剩 6 层 × 170 MB = 1.02 GB |
| KV 窗口 | 5.24 MB/会话 | 40 层 × 128 × 512 × 2 B，只驻显存 |
| head | 1.32 GB | 默认 CPU 计算，不占显存 |

### 3.2 时间模型（解码，单会话）

~~~
t_token ≈ bytes_expert_miss / B_nvme + 0.35 × bytes_pcie / B_pcie + fixed
fixed   ≈ 60 ms（采样 / head / 框架 / 同步）
bytes_expert_miss = 4.512 GB × (1 − hit_rate)
~~~

### 3.3 规划带宽档位

| 项 | 规划取值 | 用途 |
|---|---:|---|
| NVMe 保守 | 4.5 GB/s | 预算基准 |
| NVMe 上界 | 8.8 GB/s | burst 上界，小随机读、SLC 热态 |
| NVMe 最坏 | 2.5–3 GB/s | 写入竞争（下载/合并/杀毒）时 |
| PCIe H2D（pinned） | 26 GB/s | 专家上卡唯一可用通路 |
| PCIe H2D（pageable） | 约 9 GB/s | **不可用于专家流** |
| 内存带宽（RAM→CPU） | 50 GB/s 级 | 按 DDR5-5600 估算，未实测 |

所有吞吐预算同时给两个档：8.8 GB/s 与 4.5 GB/s。

在 8.8 GB/s、注意力常驻 34 层（每 token 只流 1.02 GB）条件下，解码吞吐随命中率变化：命中 0% 约 1.55 tok/s，命中 25% 约 2.0 tok/s，命中 50% 约 2.77 tok/s。带宽降到 4.5 GB/s 时折扣约 0.57，降到 3 GB/s 时再打 0.67 折。**8 GB 机器的现实区间是 0.6–2.8 tok/s，稳态最可能落在 1–2 tok/s。**

## 4. 显存：预算与槽位

### 4.1 预算账目

| 项 | 大小 | 备注 |
|---|---:|---|
| 桌面 / WDDM 预留 | 0.9 GB | 按实际写回，需可配；公式自适应 |
| CUDA / runtime 预留 | 0.35 GB | context 与 allocator |
| 注意力 / 非专家 fp8 常驻 | 34 × 170.06 MB = **5.78 GB** | 常驻层数 = floor(可用 / 170 MB) |
| 未常驻注意力层（按 token 流） | 6 × 170 MB = 1.02 GB/token | 26 GB/s → 约 39 ms，可被磁盘读掩盖 |
| 专家槽 | 24 × 18.80 MB = **451 MB** | decode 6+6 / prefill 12+12 |
| 激活 + KV 窗口 | 0.42 GB | prefill 按块；KV 窗口 5.24 MB/会话 |
| **合计** | **6.65 GB** | 余量 1.35 GB |

自适应公式：

~~~
usable_vram = vram_gb − desktop_reserve − runtime_reserve
attn_layers = min(40, floor((usable_vram − activations − slots×18.8MB − KV) / 170MB))
streamed_layers = 40 − attn_layers
streamed_bytes_per_token = streamed_layers × 170MB
~~~

开关：`--vram-reserve-mib`（默认 900+350）、`--attn-resident N`（默认 auto）、`--expert-slots N`（默认 24）、`--head cpu|fp8|bf16`。

### 4.2 槽位划分

~~~
24 槽 = 451.2 MB（专家 blob 18.80064 MB/槽）
  decode  : 6 current（当前层） + 6 staged（下一层预测/前瞻）
  prefill : 12 compute（当前 wave） + 12 staged（下一 wave，双缓冲）
  16 槽 = 300.8 MB（8+8）：可用，但 wave 减半、启动次数翻倍
  12 槽 = 225.6 MB（6+6）：无双缓冲的底线；再少会显著增加串行等待
~~~

24 槽够用，且不是瓶颈。预填充每层 384 个专家、wave=12 时是 32 个 wave；若压到无舞台的 24 个 wave，单层会多花约 9% 的 I/O 时间（GPU 计算太短，磁盘在 wave 之间空转）。解码只需要 6 个当前专家，另 6 个槽做下一层预取足够。真正影响显存的是注意力常驻，不是这 0.45 GB。若将来要腾显存：降到 16 槽只省 0.15 GB（不到一层注意力），不值得；降到 12 槽以下才开始明显掉速。

PCIe 账目（每专家 18.8 MB / 26 GB/s ≈ 0.72 ms）：

- 解码每 token 上卡的缺失专家 = 240 × (1 − hit)；hit=27% 时约 175 个 × 0.72 ms ≈ 126 ms，加上注意力流（6 层 × 170 MB ≈ 39 ms）约 165 ms/token，与磁盘读重叠（时间模型按 35% 暴露计）。
- 预填充每层整层 7.22 GB，PCIe 每次只搬一个 wave 的 12 × 18.8 MB = 225 MB；与磁盘读并行，不是瓶颈。

### 4.3 槽位语义

**槽是暂存不是缓存。** 从槽换出不丢数据（内存缓存里还有），所以不要把槽当成二级专家缓存按 LRU 独立淘汰，否则会和内存缓存抢命中率。

生命周期规则：

1. **解码当前层**：`with store.experts(layer, ids)` 持有 6 个槽的引用（refs>0），release 之前不会被换出。
2. **解码前瞻**：仅在预测置信度高（≥0.5）且槽有空余时，用 `store.prefetch_to_vram(layer+1, ids)` 把 2–6 个专家 staged；默认仍优先预取到内存（不占槽），避免和当前层抢槽。
3. **预填充**：当前 wave 的 12 个用 `with` 持有，下一 wave 的 12 个用 `prefetch_to_vram` 预载；专家读取一律 `cache=False`（不写内存缓存）。wave 结束立即 release，槽马上复用。staged 槽在 fetch 消费之前不会被驱逐，用 `staged_count` 监控泄漏。
4. **内存 pin 与槽无关**：会话热度 pin 不超过缓存的 20%，预填充不参与 pin。

### 4.4 槽位接口

- `VramSlotCache.preload(layer, expert, data) -> bool`；`is_staged` / `has` / `staged_count`；acquire 遇到 staged 直接接管（refs=1）。
- `ExpertStore.prefetch_to_vram(layer, ids, cache=False) -> 预载数`；`fetch(layer, ids, cache=False)` 返回不写内存缓存的流式记录；`stats()["vram"]["staged"]` 可观测。
- 槽不够时抛 `all VRAM expert slots are referenced or staged`。处置：先 release 当前 wave，或调大 `vram_slots`。

### 4.5 非专家驻留与总预算联动

`AttnResidencyPlan` 只看注意力预算，`VramResidencyPlan` 与槽、激活、KV、head 联动：

~~~
available = vram_gb − desktop_reserve(0.9) − runtime_reserve(0.35)      # 6.75 GB
attn_budget = available − activations(0.40) − kv(0.02) − head(0/0.66/1.32) − slots(0.451)
resident_layers = floor(attn_budget / 170.055 MB)     # auto
streamed_bytes_per_token = (40 − resident_layers) × 170.055 MB
~~~

8 GB 卡、24 槽、head 放 CPU 时：

| 项 | 值 |
|---|---:|
| available（扣桌面与 runtime） | 6.75 GB |
| 激活 + KV + head + 槽 | 0.40 + 0.02 + 0 + 0.451 = 0.871 GB |
| 注意力常驻 | auto = **34 层 = 5.78 GB** |
| 已用 / 余量 | 6.65 / **0.10 GB** |
| 流式层 | 6 层 = 1.02 GB/token 走 PCIe |

模式与边界：

- **auto（推荐）**：34 层，余量 0.10 GB 偏紧。若运行时激活与碎片波动，实际用 `--attn-resident 33`（余量 0.27 GB）。
- **full**：40 层 = 6.80 GB。8 GB 卡上 6.80 > 6.75 available，**不可行**；把槽降到 12（−0.226 GB）仍超。full 只适合 ≥10 GB 的卡（或桌面预留很小的时候 9 GB 级）。
- **N（部分驻留）**：`--attn-resident 20` → 常驻 3.40 GB、流式 20 层（3.40 GB/token，133 ms PCIe），余量 2.5 GB 可给更大的 KV / head。
- **head 放 GPU**：head fp8 0.66 GB → auto 降到 30 层；head bf16 1.32 GB → 26 层。8 GB 卡按默认走 CPU。
- **槽变化**：24 → 16 槽省 0.15 GB，auto 不会因此多出一层（仍是 34），所以单独降槽腾不出东西。
- **模型侧接口**：对未驻留层，每 token 开始时把该层 fp8 权重从一块 170 MB 的显存 scratch 拷入（与磁盘读并行）；驻留层直接引用。预填充每层权重只用一次，流式层同样处理，不额外占常驻预算。

## 5. 内存缓存

### 5.1 缓存单元与命中定义

- 缓存对象是**原始 18.8 MB fp4 blob**（w1/w2/w3 权重 + 3 段 scale 原样拼在一起）。不做 dtype 转换。
- 单元 18.8 MB：20 GB ≈ 1,086 条；30 GB ≈ 1,595 条；全模型 15,360 条（40 × 384），覆盖率 7–10%。
- **命中定义**：请求的 (layer, expert) 在内存中。命中只省磁盘读，不省 PCIe——仍然要上卡。

### 5.2 替换策略

| 策略 | 特点 | 本项目定位 |
|---|---|---|
| LRU | 实现简单，对扫描型访问差 | 基线 |
| **ARC** | T1/T2 + ghost B1/B2，自动平衡 recency 与 frequency，同容量下命中率最高 | **默认** |
| S3-FIFO | small 10% + main 90%，2-bit 频次，抗扫描、工程简单 | 备选，同容量命中率低于 ARC |
| 热度 pin | 按每层访问计数 pin 前 N 个专家，永不被驱逐 | 叠加在 ARC 上 |

容量与命中率的关系（合成路由分布下的估计，仅用于选型定档，真实路由分布必须用实测 trace 替换）：

| 缓存容量 | ARC | LRU | S3-FIFO |
|---:|---:|---:|---:|
| 8 GB | 约 15% | 约 11% | 约 8% |
| 16 GB | 约 22% | 约 19% | 约 13% |
| 20 GB | 约 25% | 约 23% | 约 15% |
| 24 GB | 约 27% | 约 25% | 约 18% |
| 32 GB | 约 30% | 约 28% | 约 21% |

**命中率强烈依赖真实路由的集中度**，上表只是保守下限的来源；规划与验收都必须换成真实 trace。

### 5.3 热度 pin

- pin 会减少可替换容量，叠加收益很小（不到 1 个百分点），不要一次 pin 太多。
- pin 预算 = 缓存容量的 **20%**，作为硬上限。
- 只 pin 观测样本足够的专家；每 128 个 token 重算一次，按"晋升 / 降级"增量调整，而不是整批替换。

### 5.4 内存预算（三情景）

| 项 | A：MTP 关（默认） | B：MTP 开 | C：内存紧张 |
|---|---:|---:|---:|
| 系统 + 应用预留 | 6.0 | 6.0 | 6.0 |
| 非专家常驻 | 9.76 | 17.78 | 9.76 |
| 其中：40 层注意力 / shared / HC | 6.80 | 6.80 | 6.80 |
| 其中：embed + head | 2.65 | 2.65 | 2.65 |
| 其中：Engram 投影 | 0.31 | 0.31 | 0.31 |
| 其中：MTP 3 层 | — | 8.02 | — |
| KV（长上下文） | 0.25 | 0.25 | 0.25 |
| pinned staging | 0.8 | 0.8 | 0.8 |
| headroom | 2.0 | 2.0 | 2.0 |
| **专家缓存** | **22.2** | **14.2** | **1.2** |
| 专家条目（18.8 MB/条） | 1,180（7.7%） | 756（4.9%） | 63（0.4%） |

说明：

- **产品默认专家缓存 20 GB 起步**（`--expert-cache-gb 20`，约 1,063 条 / 6.9% 覆盖）。A 列的 22.2 GB 是该情景下的上限，不是默认值。
- 表 A/B 按 41 GB 可用内存计，表 C 按 20 GB 计。
- **"可用内存"必须启动时实测**（`psutil.virtual_memory().available`），不能写死 47.2 GB。启动阶段其它进程占满 page cache 时，available 可能只有 20–30 GB，重启后通常 40–42 GB。`TierBudget.plan(ram_available_gb=...)` 接受实测值。
- MTP 开启等于用 8 GB 专家缓存换投机解码，默认关闭。带宽受限时净收益存疑，需要真实接受率数据再评估。

### 5.5 Windows 页锁定上限

Windows 的 page-lock 上限约为物理内存的一半（WDDM 共享预算）。因此：

- 非专家 9.76 GB + staging 0.8 GB + KV pinned 0.25 GB ≈ 10.8 GB，低于上限，安全。
- **专家缓存用普通（非 pinned）内存**，靠页表换入换出。不要把 20 GB 专家 pin 住，会触发 pinned 耗尽并挤掉系统。
- 需要更多 pinned 时用 `--pin-budget` 显式设限；分配失败要降级为普通内存，不能硬失败。

### 5.6 非专家权重

- 17.78 GB 非专家全驻内存，每 token 从内存取。
- 显存常驻 29–34 层注意力（fp8 原样），剩余 6–11 层按 token 流：每层 170 MB，26 GB/s → 6.5 ms/层；11 层约 72 ms/token，可与磁盘读并行。
- **不要**把注意力反量化成 bf16 常驻显存（340 MB/层 × 40 = 13.6 GB，不可能）。需要 bf16 计算时在 kernel 内联反量化，或每层临时 dequant 到 scratch（峰值 340 MB）。
- head：129280×5120 bf16 = 1.32 GB，默认 **CPU bf16 matvec**，约 38–41 ms/次。`model.py` 必须用 bf16 计算，不能 `.float()`——fp32 路径要 81 ms 且多占 2.65 GB 转换空间。fp8/int8 head 在 8 GB 卡上只快 5–10 ms，不值得抢先做。
- embedding：只做行 gather（10 KB/token），放内存。

### 5.7 Engram 行读

- 每 token 每 Engram 层 24 行 × 256 B = 6 KB，2 层共 12 KB。哈希 id 在当前 token 已知时就能算（`NgramHashState` 只依赖 token id），因此可以在 step 开始时预取，延迟可忽略。
- 24 个随机 256 B 读在 4 KB 页粒度下是 24 页 = 96 KB/层，2 层 192 KB/token（相对 4.5 GB 是 0.004%），**不需要专门的大缓存**。建议 128–256 MB 行缓存 + OS page cache 兜底；随机行下命中率很低（约 15%）。
- 真正要小心的是首次访问抖动：随机行在 NVMe 上约 100 μs 级，并行后可压到约 200 μs。放在 step 开始（第一个 token 的 embedding 之后）异步预取，不要在 layer 1/14 处串行等待。
- 开关：`--engram-row-cache 256MB`（默认）、`--engram-prefetch on`。
- Engine 只有在两张 Engram 表的分片都存在时才启用该路径（`all(shards exist)`），避免半表状态。
- 张量名：`layers.{1,14}.engram.{embed.weight, embed.scale, wkv.weight, wkv.scale, q_weight, k_weight}`（注意没有 `.attn.` 前缀）。

### 5.8 KV 分层

- 窗口注意力的 KV：128 行 × 512 × 2 B = 131 KB/层 → 5.24 MB/会话，**常驻显存**。
- 长上下文的压缩 KV（`compress_ratio` 层）随上下文增长，放**内存**；显存只保留当前注意力要读的尾部窗口（`--kv-resident N tokens`，默认 32K）。
- 估算（待真实值校准）：压缩 KV 约 1.3 KB/token → 128K 上下文约 166 MB/会话，4 会话约 664 MB。若按 13.7 KB/token 计，128K 就是 1.75 GB/会话，此时必须限制并发或开 KV 量化。
- 开关：`--kv-resident 32768`、`--kv-q8` / `--kv-q4`（量化，质量待测）。
- 压缩层的 KV 分层由注意力实现方接入，本模块按 0.25–1 GB 预留内存预算。

### 5.9 跨会话共享

- **全局共享**：一个 `ExpertCache`（内存）、一个 `VramSlotCache`、一个 `ShardReader` 线程池、一份热度统计。会话只持有 KV、采样状态和路由历史。
- 调度按轮转组 batch，单会话连续解码不超过 8 个 token，避免长会话饿死其他会话；p99 / p50 延迟比 ≤ 3。
- 缓存配额：全局 ARC；每个会话可 pin 自己的 top-N 作为亲和，总量不超过缓存的 20%，会话结束即释放。
- 进程内只建一个 `ExpertStore`，所有 MoE 层与会话共用。每层各建一个会重复文件句柄、缓存与线程池，内存直接翻倍。
- 活跃会话默认上限 2，硬上限 4，更多排队。并发不提高单会话速度：随机路由下并集专家近似相加（2 会话约 12 个/层、4 会话约 23 个/层、8 会话约 45 个/层，而单会话是 6 个），batching 省的是 GPU 启动开销与注意力/head 的固定成本。

### 5.10 预取对缓存的影响

预取是可选的，但对缓存有副作用，必须遵守：

1. **预取目标只放内存，不占显存槽**；槽只给当前层。
2. **预填充流一律 `cache=False`**，避免一次性 288 GB 的读把 decode 热缓存冲掉。
3. **必须带 gate**：连续若干层"预取命中率"低于阈值就关闭预取，隔一段时间再探测。没有 gate 的预取在计算窗口不足时会变成负收益（多读字节 + 抢缓存）。
4. 预取触发的路径不能改变数值结果，只影响时序。

## 6. 磁盘读取

### 6.1 索引

`ShardIndex` 解析 `index.json` 与各 safetensors header（惰性），对外提供：

- `region(name)` → 文件偏移与张量短名映射；
- `expert_blob(layer, expert)` → **两段 (shard, offset, length)**，是读取器唯一的专家入口。

索引不假设专家在文件中连续（见 2.2）。

### 6.2 读取器

`ShardReader` 每次调用给一个 blob 段，语义是同步读；批量读用 `read_many`。

- 每线程一个文件句柄；线程数默认 6，可配到 4–8。
- 同一批读取按 (layer, offset) 排序后再下发，利用磁盘的顺序性；队列深度约 8。
- 线程数不是越大越好：超过 8 之后队列开销和调度抖动会吃掉收益。

### 6.3 buffered 与 O_DIRECT 的分工

| 数据 | 读取方式 | 原因 |
|---|---|---|
| 专家 blob | `FILE_FLAG_NO_BUFFERING`（Windows 上的 O_DIRECT 等价） | 每 token 4.5 GB 的读绝不能进 OS 缓存，否则冲掉非专家常驻页 |
| Engram 表 | buffered + 自己的行缓存 | 随机小行，走 OS page cache 更划算 |
| 非专家权重 | buffered，加载后常驻 | 只在启动时读一次，之后不再读盘 |

注意：

- O_DIRECT 要求偏移与长度按 4 KB 对齐。专家 blob 的偏移不是天然对齐的，实现上要按 4 KB 向外扩读再 memmove。代价是每段最多多读 8 KB，480 段 × 8 KB = 3.8 MB/token = 0.08% 浪费，可接受。
- 反过来说：**专家读取的读放大只有 0.08%**（对齐），加上 scale 计入 blob 后的 5.9%（已包含在 18.8 MB 里）。
- **禁止整文件 mmap**：page fault 风暴会让冷数据路径慢到数倍以上。专家流只走 pread。

### 6.4 磁盘预算

| 项 | 值 |
|---|---|
| 专家总量 | 288.78 GB |
| Engram 总量 | 202.76 GB |
| 非专家总量 | 17.78 GB（全驻内存，不读盘） |
| 解码每 token 冷读 | 4.512 GB |
| 解码 480 次 pread 的队列压力 | 4–8 线程即可，不是瓶颈 |
| 规划带宽 | 4.5 GB/s 保守，8.8 GB/s 上界 |

## 7. 预填充的读盘策略

预填充与解码的读盘形态完全不同：解码每步只碰 6 个专家，预填充一上来就会触达几乎
全部的 `384 × 层数` 个专家。若把预填充的读请求和正文共享同一个缓存，一次长 prompt
就会把解码攒下来的热数据全冲掉。

因此有两条硬规则：

1. **预填充期间专家读取一律 `cache=False`。** 这些数据是一次性的，不值得占缓存。
2. **解码热缓存不被预填充污染。** staged 槽用双缓冲，预填充的读走另一侧。

### 7.1 调度顺序

预填充必须按 expert 分组读，不是按 token 顺序读：把 `(token, expert, weight)` 展平后
按 expert 排序，每个 wave 取一组连续的专家；gather 按 index 取行，scatter 用
`index_add_`。这样每个专家只从盘上读一次，而不是每个 token 都读一次。

### 7.2 中间量放在哪

- 预填充的 hidden 状态随 prompt 长度线性增长。短 prompt 可以留在显存，长 prompt
  必须放内存按块 H2D。
- attention 的临时量（当前块的 q/scores）是固定大小的块级 scratch。
- 预填充只需要最后位置的 logits；若接口要求逐 token logits，再按块跑 head。

### 7.3 分块 prefill 的正确性前提

分块预填充要求 `forward` 支持 `start_pos > 0` 且 `s > 1`。窗口 KV 按 ring 追加；
压缩 KV / compressor / indexer **只在所属层算一次**并跨块复用；共享 handoff 槽上的
全局状态必须按层顺序建好。任何按 `s = 1` 假设写的分支在分块场景下都会静默算错。
## 8. 接口与接入

### 8.1 数据流

~~~
ShardIndex ── index.json + safetensors header（惰性解析）
   │          region(name) / expert_blob(layer, expert) -> 2 段
   ▼
ShardReader ── 每线程一个句柄；buffered 或 Windows NO_BUFFERING
   │          read_blob / read_many
   ▼
ExpertCache ── 内存：ARC / LRU / S3-FIFO + pin + prefetch 线程池
   │          get / prefetch / pin_hot / hot_experts / stats
   ▼
VramSlotCache ─ 24 个 uint8 设备槽；acquire / copy_in / release
   │
   ▼
ExpertStore ── fetch(layer, ids) -> list[ExpertRecord]
   │          ExpertRecord.tensor("w1.weight" | "w1.scale" | ...)
   ▼
tinyinfer.moe：dequant_fp4_block(rec.tensor("w1.weight"), rec.tensor("w1.scale"))
~~~

### 8.2 对象与方法

| 对象 | 方法 | 语义 |
|---|---|---|
| ShardIndex | `region(name)`, `expert_blob(l, e)` | 文件偏移、两段 blob、张量短名映射 |
| ShardReader | `read_blob`, `read_many`, `stats`, `close` | 同步 / 并行字节读取 |
| ExpertCache | `get(admit=)`, `prefetch(admit=)`, `contains`, `pin`, `unpin`, `pin_hot`, `stats` | 内存缓存；`admit=False` 用于预填充流式 |
| VramSlotCache | `acquire`, `preload`, `is_staged`, `has`, `release`, `stats` | 显存暂存环 + 双缓冲舞台 |
| ExpertStore | `fetch(cache=)`, `experts(cache=)`, `prefetch_to_vram`, `release`, `prefetch`, `pin_hot`, `stats` | 门面 |
| ExpertSlotPlan | `plan(geo, slots)`, `slots_for_phase`, `table` | 24 槽 → decode 6+6 / prefill 12+12 |
| AttnResidencyPlan | `plan(geo, budget, mode)`, `is_resident` | 注意力常驻 / 流式 |
| VramResidencyPlan | `plan(vram, slots, attn_mode, head_gb)`, `table` | 显存总预算联动 |
| PrefillPlanner | `plan(routes)`, `plan_layer`, `memory`, `pseudo_code` | 逐层预填充计划 |
| TierBudget | `plan(...)`, `table()`, `io_scenarios()` | 内存 / IO 预算 |
| IoBudget | `compute(...)` | 命中率 → tok/s |

接入只需三个 API：

1. **`ExpertStore.from_store(...)`**：`ExpertStore.from_store(store, cache_bytes=20<<30, policy="arc", vram_slots=24, direct=True, device="cuda")`。进程内建一次，传给所有 MoE 层与会话。
2. **`store.experts(layer_id, ids)` + `rec.tensor(name)`**：`with store.experts(layer_id, ids) as recs:` 先取全部 6 个，再并行调用反量化。视图零拷贝，with 退出自动 release。
3. **`store.prefetch(layer, ids)` / `store.pin_hot(per_layer=20)`**：预取与热度 pin 是可选加速，且必须带 gate。

### 8.3 替换 MoE 内部缓存

原实现每层自己读 6 个张量，反量化成 bf16 后存进一个无限增长的 dict（70.8 MB/专家）。替换为：

~~~python
# 初始化（每个 MoE 层共享同一个 ExpertStore）
self._store = ExpertStore.from_store(store, cache_bytes=20 << 30, vram_slots=24, direct=True)

# forward 中
with self._store.experts(self.layer_id, needed_experts) as recs:
    for rec in recs:
        w1 = rec.tensor("w1.weight")     # uint8 [2304, 2560]，CPU 或 CUDA
        s1 = rec.tensor("w1.scale")      # float8_e8m0fnu [2304, 160]
        e = Expert(dequant_fp4_block(w1, s1), ...)
~~~

- 不在 MoE 内部缓存反量化结果；反量化每 token 做一次。
- `ExpertRecord` 的生命周期由 `with` 块管理；底层的内存缓存与显存槽不因 release 而丢失。
- expert 循环应改成"先 fetch 全部 6 个，再并行 dequant / GEMM"。
- 反量化输入仍是 HF 原始的 uint8 / fp8 张量，因此输出与现状一致（除 kernel 顺序差异）。

### 8.4 陷阱

- **不要把 `rec.tensor(...)` 的视图带出 `with` 之外**：显存槽会被复用（换 owner 后同一槽是脏数据），内存条目也可能被驱逐。跨层、跨 token 使用时先复制到自有 buffer。
- **dtype 与形状别转错**：weight 是 **uint8 packed fp4（每字节 2 个 nibble）**，不要 `.float()`，也不要 `.view(int8)` 后按整数解；scale 是 **float8_e8m0fnu [out, in/32]**。`dequant_fp4_block` 期望 `(packed [out, in//2], scale [out, in//32])`，别 reshape 成 `(in, out)`。
- **并发引用数不能超过 `vram_slots`**：decode 6+6、prefill 12+12 = 24。多会话解码先按并集算需求，否则抛 `all VRAM expert slots are referenced or staged`。
- **staged 槽必须被随后的 fetch 消费**：用 `slots.staged_count` 查泄漏，否则一个 wave 的 12 个槽会一直占着。
- **fetch 抛异常也要 release**（务必用 `with`）；`close()` 之前要等所有 prefetch future 结束。
- **`direct=True` 只用于专家流**；非专家权重仍用 buffered（17.7 GB 常驻内存）。
- **逐层预填充的 attention 必须支持 `start_pos>0` 且 `s>1`**；按 decode 的 `s=1` 路径复用会静默算错，H 的 hc 副本要保留 4 份对齐，不能先压成 mean。

## 9. 已知限制与失败模式

| 限制 / 风险 | 影响 | 处置 |
|---|---|---|
| Windows 页锁定上限（约内存一半） | 无法 pin 全部非专家 + staging | 只 pin 约 10.8 GB；`--pin-budget` 限流；失败降级为普通内存 |
| O_DIRECT 对齐 | 偏移非 4 KB 对齐，每段多读 8 KB | 按 4 KB 扩读后 memmove；480 段 × 8 KB = 0.08% 浪费 |
| 整文件 mmap | page fault 风暴，冷数据可慢数倍 | **禁止**；专家流只走 pread |
| 预取字节超过计算窗口 | 多读字节 + 抢缓存，变负收益 | 必须有 gate；`--free-compute-ms` 可调；预取只进内存不进槽 |
| 其他程序占用内存 | available 从 41 GB 掉到 20 GB | 启动时实测 available 并动态缩减缓存；最低可运行档 4 GB（212 条） |
| 桌面占用显存 | 常驻层数下降 | 自适应公式 + `--vram-reserve-mib` |
| bf16 反量化常驻 | 内存需求 ×3.8 | 集成时移除 dict 缓存，只保留 fp4 blob |
| 多会话内存膨胀 | OOM 与内存抖动 | 会话上限 4；每会话 KV 配额；全局缓存上限 |
| 逐层预填充实现差异 | 可能引入数值差异 | 以分块实现为参考，逐 token 对比 logits 与 hidden |
| 压缩 KV 尺寸未定 | 长上下文内存预算 ±一个数量级 | 按 1.3 KB/token 预留，13.7 KB/token 时限制并发或开量化 |
| 命中率依赖真实路由 | 缓存定容可能偏乐观 | 用真实 trace 复核 20/24/32 GB 三档 |
