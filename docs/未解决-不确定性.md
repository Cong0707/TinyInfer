# 未解决：forward 不确定

**这是当前最高优先级的问题。** 在它解决之前，本仓库的性能数字都只能当参考，
因为「跑得快」可能意味着「少算了东西」。

## 现象

同一个引擎实例，每次 forward 前 `eng.reset()` 清空 KV，输入完全相同：

```
ids = [[100, 200, 300, 400, 500]]

run0 vs run1: max_diff=2.3036e+01  top1=201 vs 201
run0 vs run2: max_diff=2.4117e+01  top1=201 vs 200
```

max_diff 达到 23（logits 绝对值量级也就 15~20），top-1 在 200/201 之间跳。

跨进程重跑也一样，而且更严重 —— 三次里有一次直接全是 NaN：

```
logits 前5: 200=16.775 ... finite=True
logits 前5: 1=nan 0=nan 2=nan ... finite=False
logits 前5: 200=17.387 ... finite=True
```

## 已经排除的

| 怀疑 | 验证方式 | 结果 |
|---|---|---|
| slab 覆盖层数不同 | `TI_FLAT=0` 全走 per-tensor | **仍然不确定** |
| 后台预热线程干扰 | `TI_WARM=0` | 全部 NaN（预热本身是必要的，无法这样排除） |
| 我的向量化内核 | 回退接入 | 回退后仍不确定（但它确实单独导致过 NaN，见下） |
| `_flat_setup` 异步 | 查调用点 | 它是同步的，在 forward 线程里 |

## 已经修掉的一个真问题

`_copy_blocking` 的 dirty 分支我一度把 DMA 提交到 copy stream（`_cs`）并只记了
event。但 **MoE 那条路径从不调 `wait_event`**（grep 过 moe.py，一次都没有），
它依赖「拷贝和 kernel 同一条流」来保证顺序。提交到 copy stream 就断了这个前提。
已改回当前流。

**这条修完不确定性没消失**，说明还有别的来源。

## 还没排除的方向

1. **`_async_h2d` 是否真的有序。** 它用 ctypes 直接调 `cudaMemcpyAsync`，传的
   是 `stream.cuda_stream` 这个 handle —— 理论上排在那条流上。但 torch 并不知道
   这块 device 内存被外部写过，如果 allocator 复用了它（或做了 stream 特定的
   复用优化），就可能读到旧内容。
2. **per-tensor 路径是否漏拷了某个权重。** 它按 `b._weight_paths()` 遍历，
   如果某个 tensor 不在 `_cpu_refs` 里（KeyError 被吞掉？）就会保留旧值。
3. **`reset()` 是否真的清干净。** 现在只验证了「reset 后仍然不确定」，
   没验证 reset 本身的行为。

## 建议的排查顺序

1. 先丢掉 `reset()`，改成**每次 forward 都新建进程**，看跨进程是否确定。
   这一步能把「KV 残留」和「权重内容不对」分开。
2. 拿一份**单层**做对拍：固定输入、固定权重，跑两次比中间张量。哪一层开始不同，
   问题就在那一层的装载路径上。
3. 关掉所有重叠（`TI_FLAT=0` + 同步 `copy_` 而不是 `cudaMemcpyAsync`），
   如果这样变确定，就锁定在异步 DMA 的同步语义上。
## 追加实验（16:33）

### 禁用直接 DMA 后反而全 NaN

加了 `TI_NO_ASYNC_H2D=1` 开关（让 `_async_h2d` 直接返回 False，全部退回
`copy_(non_blocking=True)`）：

```
run0 vs run1: max_diff=nan  top1=0 vs 0
run0 vs run2: max_diff=nan  top1=0 vs 0
```

**比用异步 DMA 还糟** —— 那条路至少有时给出有限值。所以在当前代码上，
「同步拷贝」不是正确的对照基线，两条路都碰上了同一个下游问题。

### 这个实验的信息量

它排除了一种可能：问题不是「异步 DMA 和 kernel 的同步语义」。因为把 DMA 换成
torch 自己的 `copy_`（torch 对这块内存有完整依赖认知）之后，NaN 反而更多。

所以要么：

- `_copy_blocking` 的 `copy_` 分支本身拿错了源数据（`data` 不是该槽位该有的内容），
- 或者问题在更上游：`_ensure` 选错了槽位、`_cpu_refs` 指向了别的层、
  或者 strided 拷贝的 view 形状不对。

### 建议从这里继续

1. 拿**单层、单张量**做对拍：固定一个 expert blob，走 `_ensure` 装进槽位，
   再和源文件内容逐字节比。这一步能直接判断「装进去的东西对不对」。
2. 如果装对了，再比 `_flat_apply` 之后的权重内容（同样逐字节比）。
3. 只有这两步都通过，再谈异步/同步 —— 在那之前，数值问题不可能是同步问题。

### 当前状态（必须说清）

**性能数字（2086ms / 0.48 tok/s）是在这份 forward 不确定的代码上测的，
不能当作有效结论。** 在不确定性查清之前，所有性能对比都可能是「少算了东西」
换来的。这条优先级高于任何优化。
## 追加（16:34）：起点代码也崩，怀疑是环境状态

回退到今天的起点提交（`7e093b4`，那时候还没做任何优化）重跑：

```
[tinyinfer] dequant fast path unavailable (CUDA_ERROR_OUT_OF_MEMORY from cuMemSetAccess)
RuntimeError: !handles_.at(i) INTERNAL ASSERT FAILED
```

**起点代码在当前环境下也跑不起来。** 所以「NaN / 不确定」至少有一部分是环境
问题，不是今天的改动引入的回归。

### 环境证据

```
  Get-CimInstance Win32_Process -Filter "Name=python.exe"   -> 空（没有残留进程）
  nvidia-smi --query-gpu=memory.used,memory.total          -> 429 MiB / 8151 MiB
  nvidia-smi --query-compute-apps=pid,used_memory         -> 34 个 PID，内存都是 [N/A]
```

**34 个僵尸 compute-app 句柄。** GPU 显存只用了 429 MiB，但驱动侧登记着 34 个
进程上下文 —— 这些是 GPU 地址空间的泄漏，进程早就退出了。

这正好解释了两件事：

1. `cuMemSetAccess` 报 OOM 却显存空闲（它要的是 device 地址空间的映射项，
   不是显存容量）；
2. 同一天里同一份代码时好时坏 —— 每次运行都在消耗一点地址空间，累积到某个
   点就开始失败，而失败的表现是随机的（`!handles_` 撞在哪层都有可能）。

### 这意味着什么

**这台机器在本次会话期间可能已经跑了几十个引擎实例，GPU 地址空间被泄漏掉
了。** 要得到可信的数值结果，需要先让它干净：

1. 重启机器（或者至少重启 NVIDIA 驱动服务）—— 这是唯一能回收这些僵尸句柄的办法；
2. 之后每轮实验之间确认 `nvidia-smi --query-compute-apps` 是空的；
3. 在那之前，**任何数值/性能结论都不可信**，包括本文档前面记录的那些。

### 我今天犯的一个错误

在发现 NaN 之后，我第一反应是怀疑自己的改动（换 kernel、换 stream），这是对的；
但连续跑了几十个实例、每次都留下一个僵尸句柄，然后继续拿这些实例的结果做
对比 —— 那时候已经在拿被污染的环境做实验了。**应该更早去看 `nvidia-smi`。**
## 追加（16:45）：NaN 与 DMA 路径无关

统计方式：同一份输入、每次新进程，各跑 4 次，数 finite 失败次数。

```
  默认（_async_h2d 直接 DMA）：       2/4 NaN
  TI_NO_ASYNC_H2D=1（全走 torch copy_）：2/4 NaN
```

**两者相同。** 所以问题不是「异步 DMA 的同步语义」—— 之前那条怀疑可以划掉了。

### 同时划掉的

`dequant_fp8` 快路径也是确定坏的，但**不是这个 NaN 的原因**：

```
  禁用快路径后的 forward:  NaN / 19.890 / NaN  （仍是 50% 左右）
```

不过它确实是个独立的正 bug，已单独禁用（见那个 commit）。

### 现在的排查空间

剩下的可能性按可疑度排序：

1. **环境（GPU 地址空间泄漏）** —— 34 个僵尸 compute-app 句柄，起点提交也崩。
   这条最应该先排除，而且只需要重启一次机器。
2. **专家装载的竞态** —— slab / cache / per-tensor 三条路径里，某条可能在权重
   还没就位时就被读。验证方法：`TI_FLAT=0` 且 `TI_NO_ASYNC_H2D=1` 同时打开
   （全部同步、全部走 torch 拷贝），如果这样还是 NaN，就与装载无关。
3. **显存碎片** —— 24 个槽位在 8GB 卡上反复换入换出，allocator 可能返回了
   正在被读的块。这个用 `torch.cuda.memory_stats()` 的 `num_alloc_retries`
   能看出来有没有真的发生过。

### 一个方法论上的教训

我在「NaN 50%」这种概率性现象上做了太多次单次对比（改一个参数、跑一次、看结果）。
**概率性 bug 必须用足够多次的统计去比较两种配置**，一次的结果什么都不能说明。
上面那个 4 次对比看起来简单，但它直接排除了我此前最怀疑的一条路。
## 追加（17:03）：slab 路径的排查记录

已排除：

| 怀疑 | 实验 | 结果 |
|---|---|---|
| 环复用竞态 | 每层 `torch.cuda.synchronize()` | 仍 2/4 NaN |
| slab 数据损坏 | 逐层检查内容 | 全部干净（absmean 158、absmax 255） |
| 尺寸越界 | 对比 total 与 buf | 最大 total = buf = 485285376，13 层全部匹配 |
| slab 内预取 | `TI_NO_FLAT_PREFETCH=1` | 仍 2/2 NaN |
| dequant 快路径 | 已单独禁用 | 仍 50% NaN |
| 直接 DMA 的同步语义 | `TI_NO_ASYNC_H2D=1` | NaN 率不变（各 2/4） |
| 环形缓冲 dtype | 检查 | `torch.uint8`，字节偏移切片正确 |

已确认的关联：

```
  TI_FLAT=0（关闭 slab）        4/4 finite
  TI_FLAT=1（开启 slab）        约 50% NaN
```

### 尚未验证的下一个假设

`_flat_setup` 里 slab 块的容量是按 `sizes[i]`（所有 tensor 字节 + 256 对齐），
而 `_flat_apply` 搬运的是 `lay[i][1]`（= `offs` 累积出的 total）。两个值理论上
应该相等，但**没有断言过**。层 7 实测：`total = 173988096`，而它的 slab 块
容量没有直接读出来对比。如果 `sizes` 大于 `total`，块尾会残留上一次（或未初始化）
的字节 —— 目前看不出哪条路径会读到那段，但这是最便宜的下一步：加一条
`assert sizes[i] == lay[i][1]`，一跑就知道。

### 当前默认

slab 已默认关闭（`TI_FLAT` 未设或非 1 时走逐 tensor 整层搬运），代价是
2893ms vs 2086ms。正确性优先。
