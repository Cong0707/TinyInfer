# 未解决：forward 不确定

**这是当前最高优先级的问题。** 在它解决之前，本仓库的性能数字都只能当参考，
因为「跑得快」可能意味着「少算了东西」。

## 现象

同一个引擎实例，每次 forward 前 `eng.reset()` 清空 KV，输入完全相同：

```
ids = [[100, 200, 300, 400, 500]]

run0 vs run1: max_diff=2.3036e+01  top1=201 vs 201
run0 vs run2: max_diff=2.4117e+01  top1=201 vs 200
```

max_diff 达到 23（logits 绝对值量级也就 15~20），top-1 在 200/201 之间跳。

跨进程重跑也一样，而且更严重 —— 三次里有一次直接全是 NaN：

```
logits 前5: 200=16.775 ... finite=True
logits 前5: 1=nan 0=nan 2=nan ... finite=False
logits 前5: 200=17.387 ... finite=True
```

## 已经排除的

| 怀疑 | 验证方式 | 结果 |
|---|---|---|
| slab 覆盖层数不同 | `TI_FLAT=0` 全走 per-tensor | **仍然不确定** |
| 后台预热线程干扰 | `TI_WARM=0` | 全部 NaN（预热本身是必要的，无法这样排除） |
| 我的向量化内核 | 回退接入 | 回退后仍不确定（但它确实单独导致过 NaN，见下） |
| `_flat_setup` 异步 | 查调用点 | 它是同步的，在 forward 线程里 |

## 已经修掉的一个真问题

`_copy_blocking` 的 dirty 分支我一度把 DMA 提交到 copy stream（`_cs`）并只记了
event。但 **MoE 那条路径从不调 `wait_event`**（grep 过 moe.py，一次都没有），
它依赖「拷贝和 kernel 同一条流」来保证顺序。提交到 copy stream 就断了这个前提。
已改回当前流。

**这条修完不确定性没消失**，说明还有别的来源。

## 还没排除的方向

1. **`_async_h2d` 是否真的有序。** 它用 ctypes 直接调 `cudaMemcpyAsync`，传的
   是 `stream.cuda_stream` 这个 handle —— 理论上排在那条流上。但 torch 并不知道
   这块 device 内存被外部写过，如果 allocator 复用了它（或做了 stream 特定的
   复用优化），就可能读到旧内容。
2. **per-tensor 路径是否漏拷了某个权重。** 它按 `b._weight_paths()` 遍历，
   如果某个 tensor 不在 `_cpu_refs` 里（KeyError 被吞掉？）就会保留旧值。
3. **`reset()` 是否真的清干净。** 现在只验证了「reset 后仍然不确定」，
   没验证 reset 本身的行为。

## 建议的排查顺序

1. 先丢掉 `reset()`，改成**每次 forward 都新建进程**，看跨进程是否确定。
   这一步能把「KV 残留」和「权重内容不对」分开。
2. 拿一份**单层**做对拍：固定输入、固定权重，跑两次比中间张量。哪一层开始不同，
   问题就在那一层的装载路径上。
3. 关掉所有重叠（`TI_FLAT=0` + 同步 `copy_` 而不是 `cudaMemcpyAsync`），
   如果这样变确定，就锁定在异步 DMA 的同步语义上。
## 追加实验（16:33）

### 禁用直接 DMA 后反而全 NaN

加了 `TI_NO_ASYNC_H2D=1` 开关（让 `_async_h2d` 直接返回 False，全部退回
`copy_(non_blocking=True)`）：

```
run0 vs run1: max_diff=nan  top1=0 vs 0
run0 vs run2: max_diff=nan  top1=0 vs 0
```

**比用异步 DMA 还糟** —— 那条路至少有时给出有限值。所以在当前代码上，
「同步拷贝」不是正确的对照基线，两条路都碰上了同一个下游问题。

### 这个实验的信息量

它排除了一种可能：问题不是「异步 DMA 和 kernel 的同步语义」。因为把 DMA 换成
torch 自己的 `copy_`（torch 对这块内存有完整依赖认知）之后，NaN 反而更多。

所以要么：

- `_copy_blocking` 的 `copy_` 分支本身拿错了源数据（`data` 不是该槽位该有的内容），
- 或者问题在更上游：`_ensure` 选错了槽位、`_cpu_refs` 指向了别的层、
  或者 strided 拷贝的 view 形状不对。

### 建议从这里继续

1. 拿**单层、单张量**做对拍：固定一个 expert blob，走 `_ensure` 装进槽位，
   再和源文件内容逐字节比。这一步能直接判断「装进去的东西对不对」。
2. 如果装对了，再比 `_flat_apply` 之后的权重内容（同样逐字节比）。
3. 只有这两步都通过，再谈异步/同步 —— 在那之前，数值问题不可能是同步问题。

### 当前状态（必须说清）

**性能数字（2086ms / 0.48 tok/s）是在这份 forward 不确定的代码上测的，
不能当作有效结论。** 在不确定性查清之前，所有性能对比都可能是「少算了东西」
换来的。这条优先级高于任何优化。
## 追加（16:34）：起点代码也崩，怀疑是环境状态

回退到今天的起点提交（`7e093b4`，那时候还没做任何优化）重跑：

```
[tinyinfer] dequant fast path unavailable (CUDA_ERROR_OUT_OF_MEMORY from cuMemSetAccess)
RuntimeError: !handles_.at(i) INTERNAL ASSERT FAILED
```

**起点代码在当前环境下也跑不起来。** 所以「NaN / 不确定」至少有一部分是环境
问题，不是今天的改动引入的回归。

### 环境证据

```
  Get-CimInstance Win32_Process -Filter "Name=python.exe"   -> 空（没有残留进程）
  nvidia-smi --query-gpu=memory.used,memory.total          -> 429 MiB / 8151 MiB
  nvidia-smi --query-compute-apps=pid,used_memory         -> 34 个 PID，内存都是 [N/A]
```

**34 个僵尸 compute-app 句柄。** GPU 显存只用了 429 MiB，但驱动侧登记着 34 个
进程上下文 —— 这些是 GPU 地址空间的泄漏，进程早就退出了。

这正好解释了两件事：

1. `cuMemSetAccess` 报 OOM 却显存空闲（它要的是 device 地址空间的映射项，
   不是显存容量）；
2. 同一天里同一份代码时好时坏 —— 每次运行都在消耗一点地址空间，累积到某个
   点就开始失败，而失败的表现是随机的（`!handles_` 撞在哪层都有可能）。

### 这意味着什么

**这台机器在本次会话期间可能已经跑了几十个引擎实例，GPU 地址空间被泄漏掉
了。** 要得到可信的数值结果，需要先让它干净：

1. 重启机器（或者至少重启 NVIDIA 驱动服务）—— 这是唯一能回收这些僵尸句柄的办法；
2. 之后每轮实验之间确认 `nvidia-smi --query-compute-apps` 是空的；
3. 在那之前，**任何数值/性能结论都不可信**，包括本文档前面记录的那些。

### 我今天犯的一个错误

在发现 NaN 之后，我第一反应是怀疑自己的改动（换 kernel、换 stream），这是对的；
但连续跑了几十个实例、每次都留下一个僵尸句柄，然后继续拿这些实例的结果做
对比 —— 那时候已经在拿被污染的环境做实验了。**应该更早去看 `nvidia-smi`。**
## 追加（16:45）：NaN 与 DMA 路径无关

统计方式：同一份输入、每次新进程，各跑 4 次，数 finite 失败次数。

```
  默认（_async_h2d 直接 DMA）：       2/4 NaN
  TI_NO_ASYNC_H2D=1（全走 torch copy_）：2/4 NaN
```

**两者相同。** 所以问题不是「异步 DMA 的同步语义」—— 之前那条怀疑可以划掉了。

### 同时划掉的

`dequant_fp8` 快路径也是确定坏的，但**不是这个 NaN 的原因**：

```
  禁用快路径后的 forward:  NaN / 19.890 / NaN  （仍是 50% 左右）
```

不过它确实是个独立的正 bug，已单独禁用（见那个 commit）。

### 现在的排查空间

剩下的可能性按可疑度排序：

1. **环境（GPU 地址空间泄漏）** —— 34 个僵尸 compute-app 句柄，起点提交也崩。
   这条最应该先排除，而且只需要重启一次机器。
2. **专家装载的竞态** —— slab / cache / per-tensor 三条路径里，某条可能在权重
   还没就位时就被读。验证方法：`TI_FLAT=0` 且 `TI_NO_ASYNC_H2D=1` 同时打开
   （全部同步、全部走 torch 拷贝），如果这样还是 NaN，就与装载无关。
3. **显存碎片** —— 24 个槽位在 8GB 卡上反复换入换出，allocator 可能返回了
   正在被读的块。这个用 `torch.cuda.memory_stats()` 的 `num_alloc_retries`
   能看出来有没有真的发生过。

### 一个方法论上的教训

我在「NaN 50%」这种概率性现象上做了太多次单次对比（改一个参数、跑一次、看结果）。
**概率性 bug 必须用足够多次的统计去比较两种配置**，一次的结果什么都不能说明。
上面那个 4 次对比看起来简单，但它直接排除了我此前最怀疑的一条路。

已排除：

| 环形缓冲 dtype | 检查 | `torch.uint8`，字节偏移切片正确 |

```
  TI_FLAT=0（关闭 slab）        4/4 finite
  TI_FLAT=1（开启 slab）        约 50% NaN
```

### 尚未验证的下一个假设

`_flat_setup` 里 slab 块的容量是按 `sizes[i]`（所有 tensor 字节 + 256 对齐），
而 `_flat_apply` 搬运的是 `lay[i][1]`（= `offs` 累积出的 total）。两个值理论上
应该相等，但**没有断言过**。层 7 实测：`total = 173988096`，而它的 slab 块

的字节 —— 目前看不出哪条路径会读到那段，但这是最便宜的下一步：加一条
`assert sizes[i] == lay[i][1]`，一跑就知道。

### 当前默认

slab 已默认关闭（`TI_FLAT` 未设或非 1 时走逐 tensor 整层搬运），代价是
2893ms vs 2086ms。正确性优先。
## 追加（17:07）：关闭 slab 会 OOM，这是一个两难

把 slab 默认关掉之后，跑性能基准直接崩在：

```
  File "deepseek/model.py", line 335, in to
    self._cpu_refs[...].to(device, non_blocking=True)
  RuntimeError: !handles_.at(i) INTERNAL ASSERT FAILED
```

原因：slab 关闭时 streamed 层走通用路径 `block.to(device)`，要把整层（174~485MB）
搬进显存；而这台卡的 24 个专家槽位已经占了 100% 显存，没有空间接这一层。

### 所以当前是一个两难

```
  TI_FLAT=1（slab 开）   能跑，2086ms，但约 50% 概率 NaN
  TI_FLAT=0（slab 关）   输出正确（4/4 finite），但会 OOM 跑不完
```

**两者都不可用于生产。** 真正的修法只有一条：把 slab 路径的 NaN 查清。

### 对后续工作的建议

优先怀疑 slab 的**数据流**而不是时序（时序已经用「每层同步」排除了）。具体：

1. 在一次 forward 里只跑**一个 streamed 层**（其余层强制常驻或用别的路径），
   把它的输出和 slab 关掉时的输出逐元素比。这能把 13~14 层的交互全部排除。
2. 如果单层就错，比对 `host[layer]` 的字节和该层 `_weight_paths()` 在 slab 关闭
   时读到的字节 —— 逐字节，不要比统计量。
3. 如果单层正确，问题在层间：检查 `flat_pos` 与 `k % _ring` 的对应关系是否
   在 `layer_seq` 有重复层（MoE 的 shared expert 可能让同一层出现两次）时错位。

### 当前仓库状态

默认 `TI_FLAT` 关闭（我上一个提交改的）。这个默认值**会让基准跑不完**，
但它保证「跑出来的数是对的」。要跑性能基准请显式 `TI_FLAT=1`，并知道那 50%
的 NaN 风险。这条两难必须在 slab 修好之后才能消掉。
## 追加（17:14）：搬运的字节是对的，NaN 在下游

加了 `TI_FLAT_VERIFY=1`：每次 slab 搬运后同步、把 `host[layer][:total]` 和
`buf[:total]` 都拉到 CPU 逐字节比，不同就打印。

结果：**一次都没打印过**（40 次搬运全部逐字节一致），但 forward 仍然 3/4 NaN。

```
  TI_FLAT_VERIFY=1：
    finite=True  sum=484919.688
    finite=False sum=nan
    finite=False sum=nan
    finite=False sum=nan
```

### 这推翻了「slab 数据流有问题」这个方向

字节能逐字节对上，说明：

- `_flat_setup` 建 slab 时的拷贝是对的
- `_flat_apply` 的整层 DMA 是对的（源、目标、长度都对）

所以 NaN 来自**搬运之后**：`set_weight` 把 block 的权重指向 `buf[o:o+n]`，然后
计算。问题可能在：

1. `set_weight` 设的 view 与 `_weight_paths()` 的 (owner, name) 对应关系，在
   slab 路径和 per-tensor 路径下不一致（两条路用的是同一份 `offs`，但
   `_flat_setup` 建 refs 时用的顺序可能和 `_flat_apply` 不同）；
2. 或者 NaN 根本不是 slab 层产生的，而是**非 slab 层**——slab 开时它们走
   per-tensor 路径，slab 关时走 `block.to()`，两条路不同。之前 A/B 对比的
   其实是「per-tensor + 部分 slab」vs「block.to」，没有单独隔离过 per-tensor。

### 下一个该做的实验

把 slab 层数压到 0 但保持 `TI_FLAT=1`（即 `_flat_state` 是 tuple 但 `host` 为空），
这样所有 streamed 层都走 per-tensor 路径。如果 NaN 出现，问题就在 per-tensor；
如果干净，问题才真的是 slab 层。

实现上要注意 `_flat_wait` 里有个分支：`if layer not in self._flat_state[0]:`
会直接 `block.to()`，正好绕过了 per-tensor。要测 per-tensor 得让层在 `lay` 里
但不在 `host` 里 —— 也就是 slab 分配成功但一层都没拷进去。
## 追加（17:21）：环数不是根因，4/4 是巧合

`TI_RING=4`（把显存环从 3 加到 4）第一次跑 4/4 finite，看起来像找到了根因。
但紧接着复跑 5 次：

```
  finite=False  finite=False  finite=False  finite=True  finite=False
```

**4/5 NaN。** 前面那个 4/4 是巧合 —— 如果真实 NaN 率是 50%，连续 4 次干净的
概率是 6.25%，完全可能发生。这是我今天第二次被小样本骗到（第一次是把
「预热进度」当成性能曲线）。

### 教训（写在这里提醒下一个接手的人）

**判断一个改动是否修好了概率性 bug，至少需要 8~10 次重复，并且和基线做对照。**
单看「连跑 4 次都过了」远远不够 —— 50% 的 bug 有 6% 概率连续过 4 次。

### 目前确认有效的唯一配置

```
  TI_FLAT=0（关闭 slab 路径）    4/4 + 之前多次 4/4 都 finite，但偶发 OOM
```

其他所有组合（slab 开 / per-tensor / 环 3 / 环 4）都会以 30~60% 概率产出 NaN。

### 已经能确定的边界

- 崩溃/NaN 只发生在「权重通过显存环形缓冲 + set_weight 间接供给」的路径上；
- 走 `block.to(device)`（权重直接是 device tensor）时是干净的；
- 搬进环的字节经逐字节验证是对的；
- 与 DMA 的同步语义无关（TI_NO_ASYNC_H2D 前后 NaN 率相同）。

所以问题最可能在 **`set_weight` 之后的可见性**：block 的权重指向刚被 DMA 写过的
device 内存，而消费它的 kernel 未必看到了写入。可能是 PyTorch 的 allocator /
stream 语义与「外部写入」的组合问题。下一步值得试：在 `set_weight` 前后各插一次
`torch.cuda.synchronize()` 并观察 NaN 率是否下降 —— 这能直接验证「可见性」假设。
## 追加（17:24）：可见性假设也不成立

在 `set_weight` 之前插一次 `torch.cuda.synchronize()`（`TI_FLAT_VIS=1`），复跑 5 次：

```
  4/5 finite（1 次 NaN）
```

基线是约 2/4。**4/5 vs 2/4 在统计上不显著** —— 5 次样本分辨不出这两个比例。
所以「内核看不到外部 DMA 写入」这个假设也不能算成立。

### 排查到这里的状态

已经排除（每条都有多次实验支撑）：

1. DMA 的同步语义（`TI_NO_ASYNC_H2D` 前后 NaN 率相同）
2. slab 建库时的数据（逐字节验证 40 次全部一致）
3. 环复用的数量（RING=4 复跑 4/5 NaN）
4. `set_weight` 之前的可见性（4/5，不显著）
5. slab 内的预取（`TI_NO_FLAT_PREFETCH=1` 仍 NaN）
6. 尺寸越界、dtype 错位（逐项核对过）

仍然成立的边界：**只要权重经过「显存环形缓冲 + set_weight」间接供给就会 NaN；
走 `block.to(device)` 就干净。**

### 下一步该往哪看

剩下的差别其实很窄了 —— 是 `_flat_apply` 里 `buf[o:o+n].view(t.dtype).view(t.shape)`
这一句产出的 tensor 与 `block.to(device)` 直接产出的 tensor 在某处不等价。
具体可查：

- `buf` 是 `torch.empty(mx, uint8, device)`，从中切出来的 view 的 **storage offset**
  和 `block.to()` 产出的 tensor 是否都从 0 开始；
- view 的 `is_contiguous()`、`data_ptr()` 对齐（某些 kernel 对 16 字节对齐敏感，
  而这正是 dequant 快路径那个 bug 的形态）；
- 权重 tensor 被多个层共享 storage 时，`set_weight` 之后上一层的 tensor 是否
  还活着并指向同一块（释放顺序问题）。

一条更快的验证路径：把 `_flat_apply` 里的 `buf` 换成**每层独立**的小 buffer
（不复用环），如果 NaN 消失，问题就锁定在「多个层共享同一块 device storage」。
## 追加（17:25）：地址对齐也排除

按上面的建议查了 `buf[o:o+n]` 切出来的 view：

  o=0        n=10240    storage_off=0        ptr%16=0  contig=True
  o=10240    n=10240    storage_off=10240    ptr%16=0  contig=True
  o=20480    n=1966080  storage_off=20480    ptr%16=0  contig=True

### 排查总账

七条假设全部排除，每条都有多次实验：

| # | 假设 | 结果 |
|---|---|---|
| 1 | DMA 异步语义 | `TI_NO_ASYNC_H2D` 前后 NaN 率相同 |
| 2 | slab 建库数据 | 逐字节验证 40 次全一致 |
| 3 | 环复用数量 | RING=4 复跑 4/5 NaN |
| 4 | set_weight 可见性 | 4/5，统计不显著 |
| 5 | slab 内预取 | `TI_NO_FLAT_PREFETCH=1` 仍 NaN |
| 6 | 尺寸越界 / dtype | 逐项核对，最大 total = buf 大小 |
| 7 | 地址对齐 | 全部 ptr%16=0、contiguous |

### 剩下的唯一线索

边界已经很窄：**权重经「显存环形缓冲 + set_weight」供给就会 NaN，`block.to()`
就干净。** 而这七条都不是。

下一个最该做的实验（比继续猜便宜）：把 `buf` 从「每层切一块的大环」换成
**每层独立的小 buffer**，不复用。如果 NaN 消失，问题就锁定在「多个层共享同一
块 device storage」—— 具体可能是上一层权重的 tensor 在新的 DMA 覆盖后仍然活着
（被某个缓存或 graph 持有），于是拿到的是别层的数据。

### 给接手的人

`docs/未解决-不确定性.md` 这一份里有完整的七次排除记录、每次的复现方式和
当时的统计数字。**不要重复这些实验**，直接从「每层独立 buffer」那条开始。
另外：这台机器上有 34 个僵尸 compute-app 句柄，起点提交也会崩在
`cuMemSetAccess OOM`，所以至少有一部分失败是环境的 —— 先重启拿到干净环境，
再做判断。
## 追加（17:29）：每层独立 buffer 也不是解

按上一条建议，给每层分配独立 buffer、完全不复用环形缓冲（`TI_FLAT_PERLAYER=1`）：

```
  4/5 finite（1 次 NaN）
```

基线是 2/4。**不显著。** 所以「多个层共享同一块 device storage」也不是根因。

### 八条假设全部否掉，这本身是信息

排除清单（每条都有多次实验）：

1. DMA 异步语义 —— `TI_NO_ASYNC_H2D` 前后 NaN 率相同
2. slab 建库数据 —— 逐字节验证 40 次全一致
3. 环复用数量 —— RING=4 复跑 4/5 NaN
4. `set_weight` 可见性 —— 4/5，不显著
5. slab 内预取 —— `TI_NO_FLAT_PREFETCH=1` 仍 NaN
6. 尺寸越界 / dtype —— 逐项核对
7. 地址对齐 —— 全部 `ptr%16=0`
8. 共享 storage —— 每层独立 buffer 仍 4/5

**结论：NaN 不在这条「环 + set_weight」链路的具体实现细节里。**

### 那还剩什么

边界事实有两条同时成立：

- 走 `block.to(device)`（权重直接是 device tensor）→ 干净
- 走环 + `set_weight`（权重是切出来的 view）→ NaN

当八条实现细节都不成立时，剩下的差别只剩**「tensor 的身份」本身**：
`block.to()` 产出的是新建的连续 tensor，而 `_flat_apply` 产出的是从大 buffer
切出来再 view 的别名。某些下游（kernel 的布局推断、in-place 优化、甚至某个
缓存的 key 用了 data_ptr）可能对这两者区别对待。

具体该查：`_weight_paths()` 返回的 `t` 被 `set_weight` 覆盖后，原来那块 CPU
pinned 内存是否还在被别处引用（比如 `b._cpu_refs` 的旧值）；以及 MoE / attention
里有没有对 `.data_ptr()` 做缓存或比较的地方。

### 时间到了，移交说明

这一轮（2026-11-09 全天）到此为止。**没有解决的问题是 forward 30~60% 概率 NaN，
且它不受 slab、DMA、环、对齐、共享 storage 影响。** 下一步的两个具体动作写上面了。

可用的配置：`TI_FLAT=0`（默认，输出正确但偶发 OOM）。
不可用：`TI_FLAT=1`（快 39%，但 30~60% NaN）。
## 追加（17:35）：默认配置也不可靠 —— 环境在恶化

把统计脚本化（`scripts/diag_nan.py`，见该文件 docstring 为什么需要它），
对**当前默认配置**（`TI_FLAT` 未设，走逐 tensor 整层搬运）跑 8 次：

```
  runs=8  nan=7  rate=0.88  finite=1
```

**88% NaN。** 而两小时前同样的代码（同样 `TI_FLAT=0`）测出来是 4/4 干净。

### 这条数据改变了整个判断

之前所有对比都默认「baseline 是好的，只是某个配置会坏」。现在看：

- 约 17:00 时：`TI_FLAT=0` → 4/4 finite
- 约 17:35 时：`TI_FLAT=0` → 1/8 finite

**同一份代码、同一个配置，失败率从 0% 涨到 88%。** 这不是代码回归（这期间
只改过诊断开关和注释），而是运行环境在恶化。

### 环境和代码的对照

```
  python.exe 残留进程     0 个
  GPU 显存                358 MiB / 8151 MiB（很干净）
  nvidia-smi compute-apps 34 个 PID，内存都是 [N/A]
```

34 个僵尸句柄从下午就没变过（不是这次会话累积的），但它们在驱动侧占着上下文
槽位。CUDA 的并发上下文数是有上限的，而每个 `Engine.from_hf` 都建一个新上下文 ——
这一整天我跑了几十个实例，很可能就是在反复消耗这个资源。

### 结论

**在当前这个环境下，这台机器上的 forward 结果不可信，任何 NaN 率对比都没有
意义。** 要拿到可信数据必须先重启（回收那 34 个句柄），然后重新跑一遍
`scripts/diag_nan.py` 建立真正的基线。

这也是为什么这一天的排查反复出现「同一个实验两次结果相反」—— 环境这个变量
一直在动，而我没有把它固定住。**做实验前先确认环境是干净的，比多做几个实验
重要得多。**
## 追加（17:40）：与配置无关，纯环境

把宿主池压到 10GB（`TI_HOST_POOL_GB=10`）再跑 5 次：

```
  runs=5  nan=4  rate=0.80
```

和默认配置的 83~88% 一样。**所以失败率与池子大小无关、与 slab 开关无关、
与环数无关。**

三次独立测量汇总：

```
  默认           8 次 7 NaN   (88%)
  默认           6 次 5 NaN   (83%)
  pool=10GB      5 次 4 NaN   (80%)
```

19 次里 16 次失败。环境参数变了三次，失败率纹丝不动。

### 这说明什么

**不是任何配置的问题，是这台机器当前的 CUDA 状态坏了。**

最可能的机制：整天几十个 `Engine.from_hf` 实例累积消耗了驱动的上下文资源
（`nvidia-smi` 里 34 个 `[N/A]` 句柄是它的表征），新分配的 device 内存于是
落在不健康的状态里，读出来是垃圾值。**为什么不总是失败、而是 80%** —— 这需要
驱动内部信息才能解释，但方向是明确的：重启一次再看。

### 交接状态（重要）

```
重启前：forward 80~88% 概率 NaN，与任何配置无关，不要在此环境做对比实验
重启后：先跑 python scripts/diag_nan.py --runs 20 建立真基线
```

**今天后半段所有「A 配置比 B 配置好」的结论都必须作废重测**，包括：

- slab 开关对 NaN 的影响（当时 A 组 1/3、B 组 4/4，本来就是小样本）
- 环数 3 vs 4（4/4 那次已确认是巧合）
- 「TI_FLAT=0 是干净的」（后来同配置测出 88% 失败）

真正可信的只有那四个 bug 修复本身，它们不依赖 NaN 率对比：
pinned 路径没走、`copy_` 缺 non_blocking、dequant 快路径非法寻址、
copy stream 与 MoE 的同步缺口 —— 每一条都有独立于 NaN 的证据（计数、
profiler、fp64 对拍、代码阅读）。
## 追加（17:46）：找到 NaN 率的决定因素 —— 显存压力

既然 `TI_SLOTS` 是真正生效的（见 `docs/幽灵开关.md` 的纠正），用它做了一次
有意义的对比：

```
  默认（24 个专家槽位，显存占满 100%）  8 次 7 NaN  (88%)
  同配置                                6 次 5 NaN  (83%)
  TI_SLOTS=8                            5 次 1 NaN  (20%)
  TI_SLOTS=8                            6 次 1 NaN  (17%)
```

**少槽位那两组累计 11 次里 2 次失败（18%），默认那两组累计 14 次里 12 次失败
（86%）。** 这个差异远超样本噪声（18% vs 86%，n=11/14）。

### 这意味着什么

NaN 率和**显存压力**强相关。24 个槽位在这张 8GB 卡上正好把显存占满（`free=0.00GB`），
而当显存一点余量都没有时，一些运行期分配（KV 增长、attention 临时张量、
dequant 的 fp32 中间量）会落到不健康的状态 —— 分配的地址可能是有效的，但驱动
在这块卡上的行为已经不可靠了。

这和之前查到的另一条一致：`!handles_ INTERNAL ASSERT` 也只在显存耗尽时出现
（`www.` 那批 OOM 全是池子/槽位吃满的时候）。

### 这改变了优化方向的优先级

之前一直在追「怎么把槽位用到极限」（24 个，覆盖 10% 的一步需求）。现在看，
**把显存吃到 100% 本身就是不可靠的**。正确的做法应该是：

```
  槽位数 = 显存能给的上限 - 运行期需要的余量
```

而这个余量不该手调，应该由训练器扫 —— 但它扫的指标要改成「连续 N 步无 NaN 的
最大槽位数」，而不是「每步耗时最短」。

### 未验证的

`TI_SLOTS=8` 仍有 18% 失败，说明余量还不够。下一步该扫 4/6/8 找能稳定到 0%
的那个点，然后再看它的性能代价。**这是重启之后第一件该做的事**（当前环境下
漂移太大）。
## 追加（17:50）：找到了稳定配置 —— TI_SLOTS=4，11/11 无 NaN

沿「显存压力」那条线索往下扫槽位数：

```
  24（默认，显存占满）   8 次 7 NaN  (88%)  +  6 次 5 NaN  (83%)
   8                    5 次 1 NaN  (20%)  +  6 次 1 NaN  (17%)
   4                    5 次 0 NaN  ( 0%)  +  6 次 0 NaN  ( 0%)
```

**`TI_SLOTS=4`：累计 11 次连续干净。** 这是今天第一次拿到 0% 失败的配置。

（11/11 干净能排除的失败率上限约 26%，所以严格说还不够硬；但和 24 槽位的
86%（14 次里 12 次失败）相比已经是压倒性的差异。）

### 这个结果的含义

**那 86% 的 NaN 不是代码 bug，是「显存被吃到 0 余量」的后果。**

24 个槽位在这张 8GB 卡上把显存占满（`free=0.00GB`），此时：

- 运行期的临时分配（KV 增长、attention 临时张量、dequant 的 fp32 中间量、
  MoE 的 workspace）没有余量可用；
- `cuMemSetAccess` 会报 OOM（它要的是 device 地址空间的映射项）；
- `!handles_ INTERNAL ASSERT` 也在这种状态下出现。

减少槽位 = 给运行期留出真实余量 = 失败率归零。**这不是「牺牲性能换正确性」，
而是「之前的配置本来就是不可运行的」** —— 一个 86% 概率输出垃圾的配置，
它的性能数字（2086ms / 0.48 tok/s）没有意义。

### 待办（重启后第一件事）

1. 用 `python scripts/diag_nan.py --runs 30 --env TI_SLOTS=4` 把置信度做硬；
2. 扫 4 / 5 / 6 找「稳定且最快」的点 —— 现在知道上限不是「显存能塞几个」，
   而是「塞满之后还能不能算对」；
3. 把槽位数的默认值改成「显存上限 - 运行期余量」，而不是「显存上限」。
   余量不该是常数，应该由 `scripts/diag_nan.py` 的失败率反馈出来 ——
   这正是训练器该扫的东西，且指标是「无 NaN 的最大槽位」而不是「最快」。

### 这条推翻今天的大部分性能结论

所有在 24 槽位下测出来的 step 时间（2086ms、2052ms、2178ms、2893ms …）都
来自一个 86% 概率输出错误的配置。**在 `TI_SLOTS=4` 上重测才有意义。**
