# 未解决：forward 不确定

**这是当前最高优先级的问题。** 在它解决之前，本仓库的性能数字都只能当参考，
因为「跑得快」可能意味着「少算了东西」。

## 现象

同一个引擎实例，每次 forward 前 `eng.reset()` 清空 KV，输入完全相同：

```
ids = [[100, 200, 300, 400, 500]]

run0 vs run1: max_diff=2.3036e+01  top1=201 vs 201
run0 vs run2: max_diff=2.4117e+01  top1=201 vs 200
```

max_diff 达到 23（logits 绝对值量级也就 15~20），top-1 在 200/201 之间跳。

跨进程重跑也一样，而且更严重 —— 三次里有一次直接全是 NaN：

```
logits 前5: 200=16.775 ... finite=True
logits 前5: 1=nan 0=nan 2=nan ... finite=False
logits 前5: 200=17.387 ... finite=True
```

## 已经排除的

| 怀疑 | 验证方式 | 结果 |
|---|---|---|
| slab 覆盖层数不同 | `TI_FLAT=0` 全走 per-tensor | **仍然不确定** |
| 后台预热线程干扰 | `TI_WARM=0` | 全部 NaN（预热本身是必要的，无法这样排除） |
| 我的向量化内核 | 回退接入 | 回退后仍不确定（但它确实单独导致过 NaN，见下） |
| `_flat_setup` 异步 | 查调用点 | 它是同步的，在 forward 线程里 |

## 已经修掉的一个真问题

`_copy_blocking` 的 dirty 分支我一度把 DMA 提交到 copy stream（`_cs`）并只记了
event。但 **MoE 那条路径从不调 `wait_event`**（grep 过 moe.py，一次都没有），
它依赖「拷贝和 kernel 同一条流」来保证顺序。提交到 copy stream 就断了这个前提。
已改回当前流。

**这条修完不确定性没消失**，说明还有别的来源。

## 还没排除的方向

1. **`_async_h2d` 是否真的有序。** 它用 ctypes 直接调 `cudaMemcpyAsync`，传的
   是 `stream.cuda_stream` 这个 handle —— 理论上排在那条流上。但 torch 并不知道
   这块 device 内存被外部写过，如果 allocator 复用了它（或做了 stream 特定的
   复用优化），就可能读到旧内容。
2. **per-tensor 路径是否漏拷了某个权重。** 它按 `b._weight_paths()` 遍历，
   如果某个 tensor 不在 `_cpu_refs` 里（KeyError 被吞掉？）就会保留旧值。
3. **`reset()` 是否真的清干净。** 现在只验证了「reset 后仍然不确定」，
   没验证 reset 本身的行为。

## 建议的排查顺序

1. 先丢掉 `reset()`，改成**每次 forward 都新建进程**，看跨进程是否确定。
   这一步能把「KV 残留」和「权重内容不对」分开。
2. 拿一份**单层**做对拍：固定输入、固定权重，跑两次比中间张量。哪一层开始不同，
   问题就在那一层的装载路径上。
3. 关掉所有重叠（`TI_FLAT=0` + 同步 `copy_` 而不是 `cudaMemcpyAsync`），
   如果这样变确定，就锁定在异步 DMA 的同步语义上。
## 追加实验（16:33）

### 禁用直接 DMA 后反而全 NaN

加了 `TI_NO_ASYNC_H2D=1` 开关（让 `_async_h2d` 直接返回 False，全部退回
`copy_(non_blocking=True)`）：

```
run0 vs run1: max_diff=nan  top1=0 vs 0
run0 vs run2: max_diff=nan  top1=0 vs 0
```

**比用异步 DMA 还糟** —— 那条路至少有时给出有限值。所以在当前代码上，
「同步拷贝」不是正确的对照基线，两条路都碰上了同一个下游问题。

### 这个实验的信息量

它排除了一种可能：问题不是「异步 DMA 和 kernel 的同步语义」。因为把 DMA 换成
torch 自己的 `copy_`（torch 对这块内存有完整依赖认知）之后，NaN 反而更多。

所以要么：

- `_copy_blocking` 的 `copy_` 分支本身拿错了源数据（`data` 不是该槽位该有的内容），
- 或者问题在更上游：`_ensure` 选错了槽位、`_cpu_refs` 指向了别的层、
  或者 strided 拷贝的 view 形状不对。

### 建议从这里继续

1. 拿**单层、单张量**做对拍：固定一个 expert blob，走 `_ensure` 装进槽位，
   再和源文件内容逐字节比。这一步能直接判断「装进去的东西对不对」。
2. 如果装对了，再比 `_flat_apply` 之后的权重内容（同样逐字节比）。
3. 只有这两步都通过，再谈异步/同步 —— 在那之前，数值问题不可能是同步问题。

### 当前状态（必须说清）

**性能数字（2086ms / 0.48 tok/s）是在这份 forward 不确定的代码上测的，
不能当作有效结论。** 在不确定性查清之前，所有性能对比都可能是「少算了东西」
换来的。这条优先级高于任何优化。
