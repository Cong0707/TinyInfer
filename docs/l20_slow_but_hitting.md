# L20 实测：命中了，但还是很慢（2026-11-08 15:36）

## 数据（40 层全驻留，1057 槽位）

```
rows=1  1181 ms/step  0.85 tok/s  hit=1573 miss=197   finite=True
rows=2  2290 ms/step  0.87 tok/s  hit=2018 miss=1261  finite=False
rows=4  1260 ms/step  3.18 tok/s  hit=1896 miss=1788  finite=True
rows=8   994 ms/step  8.05 tok/s  hit=1985 miss=2788  finite=True
```

## 关键矛盾

`rows=1` 的命中率 = 1573/(1573+197) = **89%**，几乎不搬运，
但单步仍要 **1181ms**。

预算：40 层 x 0.95ms(纯 MoE) = 38ms。
**实测慢 31 倍，而专家搬运已经被排除。**

## 更反常的：rows 越多越快

```
rows=1 -> 1181ms
rows=2 -> 2290ms   （异常，可能是 NaN 路径的额外开销）
rows=4 -> 1260ms
rows=8 ->  994ms   （最快）
```

8 行比 1 行还快 16%。这与「batch 越大越慢」的常识相反，
说明有**固定的每步开销**（约 1 秒），而它与 batch 无关。

## 这个固定开销是什么

每步约 1000ms 的固定开销，候选：

1. **同步点**：每层/每步一次的 `cuda.synchronize()` 或 stream 等待
2. **`_miss_scan` 内核**：虽然命中，但每个专家都要扫一遍并 D2H
3. **`layer_begin()` / `idle()`**：每层调一次的事件操作
4. **host-mapped 队列轮询**：卖家线程与 GPU 的交互
5. **FP8 反量化缓存**：`dequant_fp8_block` 每层重建

40 层 x 25ms/层 = 1000ms。所以是**每层约 25ms 的固定开销**。

## 下一步（明确）

用 `torch.cuda.Event` 逐层计时，或者用 `TI_PROF=1`（如果有）看每层耗时。
最直接的办法：把 40 层切成 4 组，分别计时，看是否线性。

## 这不是推倒重来能解决的

引擎的结构（GPU 下单 / CPU 推送 / 槽位覆盖）本身是对的 ——
命中 89% 证明它工作。**问题在每层的固定开销上**，这是个性能调优问题，
不是架构问题。
