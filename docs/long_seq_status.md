# 长序列：修好 1K 的形状 bug，但 2K 仍有 NaN（2026-11-08 15:03）

## 本轮修好的（确定）

`compressed_attention.py:332` 的形状 bug：

```
修复前  N=1024 -> NaN（没有异常，被 except 吞掉）
修复后  N=1024 -> finite
```

原因：`grp0` 在 s>1 时是 `[b, s]`，`.unsqueeze(1)` 变成 `[b, 1, s]`，
加 `[1, ng]` 广播失败。修法：取最后一列 `grp0[:, -1]`。

这条修复独立有效（`probe_1024tb.py` 单层直接调用：`OK finite=True`）。

## 新发现：结果对**具体 token 序列**敏感

```
probe_long2.py   (base*400)[:2048]   -> finite=True  absmax=19.84
probe_one.py     (base*2000)[:2048]  -> finite=False absmax=nan
```

同样长度、同样模型、同样 4 层，**只是重复次数不同**（内容不同），结果一个正常一个 NaN。

## 这意味着什么

1. 之前「2K 全部正常」的结论**不成立** —— 那只是某一个序列凑巧正常。
2. 还有别的 bug，只在特定输入下触发。
3. 排查必须用**多个不同序列**交叉验证，不能只测一个长度一次。

## 4096 是 OOM

```
N=4096  CUDA driver error: out of memory
        vram free=0MB/8124MB alloc=5325MB
```

8GB 卡上 4 层模型跑 4K token prefill 会 OOM。这是显存限制，不是 bug。

## 本轮的另一处改动

给 `fp8_linear` 的 M=1 分支加了「反量化 + bf16 matmul」兜底。
单独测 `fp8_linear(x[1,1280], w[32768,1280])` 是 `OK (1, 32768)`。

**但它在引擎里没有被触发过**（2K 的 NaN 不是抛异常，是数值问题），
所以这个兜底的**收益尚未验证**。它只解决「最后一块只有 1 行」这一种情况。

## 下一步

1. 用**多个不同序列**测同一长度，确认 NaN 的触发条件（是内容相关，还是位置相关）
2. 如果与内容相关，看是不是某个专家路由组合的问题
3. 如果是位置相关（比如某个 ratio 边界），那就更容易定位

## 现状总结

| 长度 | 状态 |
| --- | --- |
| 128-1024 | 正常（多个序列验证过）|
| 2048 | **部分序列 NaN** |
| 4096 | OOM（8GB 限制）|
