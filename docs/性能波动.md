# 性能波动：为什么同一份代码会跑出两种结果

这份文件记录一类特别难查的问题：**代码没变、配置没变，性能却差一倍。**

## 症状

连续三次运行，同一份代码、同一台机器：

```
  slab 10 层  2083ms
  slab  6 层  4060ms
  slab  7 层  3671ms
```

看起来像性能退化，实际是**启动瞬间读到的宿主内存状态不同**：pool 被算成
11.6 / 9.1 / 9.9 GB，slab 能装几层跟着变，而 slab 层数直接决定每一步要按
tensor 逐个搬多少层 —— 差 4 层就是差一倍时间。

日志里的直接证据（不用猜，它会自己说出来）：

```
  pool exhausted at layer 19 (12.7/12.7GB used)
  pool exhausted at layer 10 ( 8.8/ 8.9GB used)
```

## 修法

1. **slab 上限不再用 `_pool.free`**。那是启动那一刻的剩余量，别的进程一占就变。
   改成按 `_pool.total` 给份额 —— 它在 claim 成功之后就固定了。
2. **pool 大小同时受两条约束取小**：
   - `物理总量 x 比例`：一次开机内不变，定基调
   - `瞬时可用 x 比例`：只在内存确实紧张时收紧

### 一个静默失效的教训

第一版用的是 `hw_plan.ram_gb_total`，但 `Plan` 里**没有这个字段**。
`getattr(..., 0)` 拿到 0，约束静默失效，现象照旧 —— 而代码看起来已经修好了。

第二版改用 `budget.total`（HostBudget 初始化时从 `_physical_ram()` 取好）。

**静默失效的约束比没有约束更危险**，因为它伪装成了已修复。写这类「取一个量、
做约束」的代码时，拿不到值应该报错或至少打一行日志，不能默默当成 0。

## 修完之后

配置稳定了（连续两次都是 slab 13 层 / pool 12.4GB），但 step 仍在 3000~3900ms
之间波动。那是宿主环境噪声（别的进程、页缓存温度、warm 线程进度），不是配置
在变。

**报告性能时必须说清是哪一种波动。** 「配置在跳」是 bug，「环境在抖」是要在
测量方法上处理的噪声（预热到稳定 + 多轮取中位数）。

## 没生效的开关（查过、还没修）

`TI_CACHE_GB`：设 5 实际给 15.2GB，设 3 实际给 10.3GB。覆盖逻辑被后续计算
盖掉了。要调 cache 大小时先验证这个开关真的生效（打印 plan 里的 cache_bytes
对比），别凭想象。

同类问题在 AUDIT-dead-switches.md 里还有一批（11 个「注释承诺、代码从不读」
的幽灵开关）。**调任何参数之前，先确认它真的被读到。**

## 测量纪律

1. 每组配置必须先预热到稳定：连续 3 步的读盘量变化 < 10%（本机约 28 步）。
2. 多轮取样取中位数，记录 spread。spread 大的那组本身就没测准，不参与比较。
3. 一次测量不下结论。本机同一配置相邻两次能差 50%。
4. 参数搜索是训练器的活（`python -m tinyinfer.tune`），不是手工 A/B。
