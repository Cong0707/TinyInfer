# 硬件

引擎不认机器型号，只认这台机器上实测到的三组数字：可用显存、可用内存、盘速。所有
决策——常驻层数、槽位数量、缓存配额、prefill 分块——都是从这三组数解出来的。

`scripts/plan_matrix.py` 可以把规划器对着假想机器的参数表跑一遍（不需要 GPU），
用来在买卡或借卡之前先看它会被什么卡住。

## 两类机器

| 类别 | 瓶颈 | 抓手 |
| --- | --- | --- |
| 6~12GB 显存 | 盘（专家缺失） | 更快的盘、更大的内存缓存、缓存淘汰策略；槽位帮不上什么忙 |
| 16GB 显存 | 盘，部分缓解 | 槽位开始有意义 |
| 24GB 及以上 | 算力 | 全部层常驻、槽位能覆盖一个 decode 步的全部专家，此时瓶颈变成纯计算 |

## 显存装不下全部层时

尾部若干层逐 token 走 H2D 拷贝。一层的权重大约一两百 MB 量级，乘上层数就是每 token
要过的字节数。这类机器上 decode 的时间几乎全花在这条搬运上，算力反而不是瓶颈。

把「内存够大、全部专家能驻留内存」这件事做对之后，同一台 8GB 机器的 prefill 快了
一个数量级——因为之前每次都在读盘。

## 显存能装下时

槽位池能被规划到覆盖「一个 decode 步可能路由到的全部专家」（topk × 层数）。此时
decode 不再触碰磁盘，时间塌缩成纯计算：每层 topk 次专家 GEMV 加若干稠密 GEMM。

嵌入表在这种配置下会被规划器挪回主机内存，换来更多槽位——每 token 一次 10KB 量级的
行查找只值约 1ms，而多出来的槽位能省掉约 1s。

## 容量口径

在给定显存下，能撑多少条并发由两条独立约束取小：

1. **KV 显存**：一条会话的 KV 与其上下文长度成正比，长上下文会主导。
2. **专家槽位**：并发会话越多，一层里被路由到的专家并集越大，槽位需求随并发增长。

只看一条会高估。两条都在规划器里算，启动时打印的 `slots=` 就是取小之后的结果。

## 已知的物理下限

盘读、PCIe、显存带宽各自有上限，任何实现都不可能突破。要判断「还差多少」应该拿
实测值比这些下限，而不是比另一台机器的实测值——后者混了太多配置差异。
