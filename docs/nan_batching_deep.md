# 顺序修复无效，但定位更精确了（2026-11-08 12:53）

## 修了但没用的

把 `moe.py` 分批循环里的 `torch.cuda.synchronize()` 移到 `_o.clone()` 之前 ——
NaN 完全没有变化（BS=3 -> [10]，BS=4 -> [8,9]）。**假设错误，已保留该改动**
（顺序本身是对的，但不是 bug 成因）。

## 更精确的调用结构（hook 抓到）

```
gate: x=(11, 5120) w=(11, 6) idx=(11, 6)
  _forward_gpu_only: x=(1,11,5120) xf=(11,5120) idx=(11,6) rows=11 nexp=66
  _forward_gpu_only: x=(4, 5120)   xf=(4,5120)  idx=(4,6)  rows=4  nexp=24
  _forward_gpu_only: x=(4, 5120)   xf=(4,5120)  idx=(4,6)  rows=4  nexp=24
  _forward_gpu_only: x=(3, 5120)   xf=(3,5120)  idx=(3,6)  rows=3  nexp=18
```

关键：**外层那次调用 `rows=11` 是「整批」进去的，分批发生在 `_forward_gpu_only`
内部的递归**，不是外层循环。所以 `_moe_bs` 作用于每一次递归。

BS=4 时切分是 4+4+3，最后一批 3 行不再分批。NaN 在 [8,9] —— 正是**第三批
（索引 8,9,10）的前两行**，第三行 p10 在这一批里反而是好的。

## 现在的确定事实

| 批次 | 切分 | NaN |
| --- | --- | --- |
| 2 | 2x5+1 | 无 |
| 3 | 3+3+3+2 | [10] |
| 4 | 4+4+3 | [8,9] |
| 6 | 6+5 | [10] |
| 8 | 8+3 | 无 |
| 11 | 11 | 无 |

规律尝试：坏的行 = 「批次起点之后的行」？

- BS=3: 批次起点 0,3,6,9。坏的是 10（第四批第二行）
- BS=4: 批次起点 0,4,8。坏的是 8,9（第三批前两行）
- BS=6: 起点 0,6。坏的是 10（第二批第五行 = 最后一行）

**没有一致的行偏移。** 但注意：坏的行数 = 11 - 某个「完整批次数 x 批次大小」。

另一种可能：`_scratch` / `_sids_buf` / `_aq_buf` / `_ascb` 这些**按批大小分配的
buffer 在批次之间没有彻底重置**，导致残留数据混入。

## 下一个探针

在 `_forward_gpu_only` 的递归分支里，每批之前把所有 `_xxx_buf` 打印一遍大小和
第一个元素，看批次间的复用是否干净。
