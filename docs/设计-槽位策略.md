# 设计：槽位策略

## 问题

槽位少的时候，如果「谁来谁占一个、满了就覆盖任意一个」，会退化成永远在搬：每个专家
都被搬进来，下一层一用就被顶掉，一次都命中不了。这不是池子小的问题，是**没有策略**
的问题。

## 分级

把槽位上的专家按紧迫程度分成三级：

| 级别 | 含义 | 覆盖权限 |
| --- | --- | --- |
| urgent | 本层当前正在用的专家 | 可以覆盖 non-urgent 与历史 |
| non-urgent | 已预取、下一层会用到的专家 | **只能填空槽**，不能覆盖别人 |
| 历史 | 之前用过、当前没有引用的专家 | 最先被覆盖 |

关键规则：**non-urgent 只能填空槽。** 否则当前层刚搬完的专家会被自己的预取顶掉，
一步之内反复搬运，命中率归零。

## 引用计数

专家被当前层引用期间 `refs > 0`，此时不可回收。每层 forward 结束后释放，状态从
「使用中」转「已暂存」——数据留着，下一步再命中就是最快的路径。

```refs``` 只增不减是这类系统的经典故障：全部槽位卡在不可回收，`acquire()`
一个可回收的槽都找不到，kernel 拿到 -1 当偏移寻址，读出来是别的专家的字节。

## 满池时的行为

`acquire()` 在池满时返回 -1，**不替调用方决定要不要等**。调用方必须把 -1 当成
「这个专家本轮不在槽位里」，走缺失表路径去搬。这比在原地阻塞更安全：阻塞会把
「拿不到槽位」变成「整条流水线停住」。

## 回收时必须清表

槽位被回收后，设备侧的 `(层, 专家) -> 槽位号` 映射表里对应项必须置 -1。不清的话，
下一层路由到同一专家会静默读到别人的权重——没有报错，只有输出慢慢变坏。
