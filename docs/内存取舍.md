# 内存分配的取舍：一次被数据推翻的「优化」

这份文件记录一个看起来显然、实测却被推翻的优化方向。**结论是反直觉的，
所以要把证据留全，免得下一个人再走一遍。**

## 背景：pool 里的三方竞争

宿主池（pinned）只有一块，三方要分：

1. **cache**：专家权重的内存缓存（一步要 240 个专家，命中就省一次读盘）
2. **slab**：streamed 层权重的连续副本（进 slab 的层，每步一次 DMA；
   没进的层，每步要按 tensor 逐个搬 30 次）
3. **build_pool**：启动时读进来的权重（读进 pool 就不算额外申请内存）

## 尝试：绕开 build_pool 给 slab 让路

**推理**：streamed 层的权重马上要拷进 slab，而 slab 切自同一块 pool ——
权重在 pool 里白占一份。绕开之后 slab 应该能装更多层。

**实测确实如此**：slab 从 13 层涨到 29~30 层。

```
  slab 13/33  (pool exhausted at layer 20)
  slab 29/33  (pool exhausted at layer 36)
```

**但性能反而更差**：

```
  不绕过  slab 12 层  2261ms
  绕过    slab 29 层  3602ms
```

## 为什么错了

build_pool 的作用不只是「省一次内存申请」。它让**没进 slab 的那部分层的权重
留在 pool 里**。绕开之后这些权重进了私有内存，之后要么被释放、要么每次要用
时重新读盘 —— 于是「slab 层数变多」的收益，被「剩下的层每步重新读盘」的代价
盖过去了。

换句话说：slab 解决的是**每步的 DMA 次数**，build_pool 解决的是**每步的读盘
次数**。这两个不是同一个瓶颈，不能拿一个去换另一个。

## 顺带测到的：cache 调大也变慢

```
  cache=6   slab 30 层  3602ms
  cache=8   slab 22 层  5702ms
  cache=10  slab 25 层  6351ms
```

cache 变大反而慢，且 slab 层数和 cache 大小不单调（因为 pool 总量本身在变）。
这说明在这个配置下，**专家读盘已经不是主要瓶颈** —— 加 cache 从别处挤走了
更有用的东西。

## 当前配置的取舍

slab 12~13 层 / cache 约 0.5GB（默认）。这个组合不是最优的证明，只是目前
实测最快且能稳定跑通的。要再往前推进，得先回答「每步的时间到底花在哪」，
见 `性能结构.md`。

## 教训

**「省内存」和「省时间」不是一回事。** 把一份权重从 pool 挪到私有内存，
账面上内存占用更合理了，但运行时行为可能完全相反 —— 因为 pool 里的那份权重
是**可复用的**，私有内存里的那份不是。

判断这类改动，唯一可靠的办法是**测端到端时间**，不是看内存账。
