# 部署

## 1. 机器需要什么

| 项 | 最低 | 它决定什么 |
| --- | --- | --- |
| GPU | 任意 CUDA 卡，≥ 8GB | 能常驻多少层、有没有专家槽位 |
| CUDA toolkit | 12.x 以上，`nvcc` 在 PATH 里 | 能否编译 kernel |
| 主机内存 | 16GB（建议 47GB 以上） | pinned 层块 + 专家缓存能开多大 |
| 磁盘 | checkpoint 所在卷的读速 | **直接决定 decode 速度** |
| Python | 3.12 以上 | venv 会建成 3.13 |

没有 FPGA、没有特殊硬件。引擎不依赖任何第三方 kernel 框架，所有 kernel 由
`scripts/build_native.sh` 用 nvcc 现编成本仓库独占的 cubin。

## 2. 权重

HF safetensors 形式的 DeepSeek-V4.1-Flash。放在最快的卷上。多块盘可以条带拼起来：

    ./start.sh --model '/mnt/nvme0/model;/mnt/nvme1/model'

## 3. 安装

    git clone <repo> tinyinfer && cd tinyinfer
    ./scripts/bootstrap.sh

它建 venv、按本机驱动装 torch、把包按 editable 装上、并针对本机 GPU 编译 kernel。

torch 不钉版本是有意的；默认轮子和驱动不匹配时：

    TORCH_INDEX=cu130 ./scripts/bootstrap.sh

## 4. 为目标准备 kernel

`bootstrap.sh` 会探测架构，在「就在这台机器上跑」时这是对的。交叉编译或驱动报出的
架构不对时，显式指定：

    ARCH=sm_90 ./scripts/build_native.sh

cubin 的架构必须与运行时的卡匹配，否则加载时报 `cuModuleLoad 209`。编译产物不入库。

## 5. 启动

    ./start.sh --model /path/to/ckpt --port 8000

启动会打印规划结果，形如：

    [tinyinfer] <卡> vram=..GB ram=..GB -> layers=40/40 stream=0 buf=0
                slots=1057 cache=274.3GB chunk=132 embed=gpu head=gpu

**先看这一行再谈性能。** 它同时说明：全部层是否常驻、有多少专家槽位、内存缓存能装
多少、prefill 分块多大。同一份代码在不同机器上这一行完全不同，性能差异几乎全部由它
解释。

## 6. 冷启动顺序

启动之后磁盘立刻开始工作，不等第一个请求。请求到达时直接读它需要的那部分，不排在
预热后面。所以：

- 进程刚起来时 GPU 利用率低、磁盘繁忙，是正常的；
- 第一批请求可能比稳态慢，因为专家还没全部进内存；
- 稳态的标志是槽位覆盖一个 decode 步的全部专家，此时每步读盘为零。

## 7. 依赖边界

运行时依赖只有 torch、transformers、fastapi 一类常规件。**没有 tilelang、没有 vllm
包、没有编译期扩展。** kernel 走 CUDA driver API 直接加载 cubin，不经 torch 头文件。

## 8. 尚未验证的部分

- 多卡张量并行 / 专家并行：代码路径存在，单卡上无法验证。
- 1M 上下文端到端：容量算过，没真跑过。
- 压缩层的拼批一致性：单次 forward 不产生压缩组，缺跨步测试脚手架。
- KV 换出接进 forward：调度层的 park/resume 工作，注意力侧的保存/恢复没有端到端验证。
