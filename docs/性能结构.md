# 性能结构与瓶颈

这份文件记录**一次 decode step 的时间到底花在哪**，以及每一项是怎么测出来的。
目的不是给出某个数字，而是让人能在一台新机器上重新测一遍同样的东西。

## 测量方法

三个工具，按精度从粗到细：

1. **墙钟 vs GPU 时间**：在 forward 外包两个 CUDA event。如果 `wall ≈ gpu`，说明
   GPU 真的在忙；如果 `wall >> gpu`，说明在等 CPU（提交慢、Python 编排慢）。
   这一步决定后面往哪个方向查。
2. **torch profiler（只看 CUDA）**：给出每个 kernel / memcpy 的实际设备耗时。
   注意用 `self_device_time_total`（新版 torch），不是 `self_cuda_time_total`。
3. **`_DMA_STATS`**：自建的计数，记 `ok_calls / ok_bytes / rc_fail / fallback_path`。
   用来回答「异步 DMA 路径真的被走了吗」——这个问题 profiler 答不了，
   因为退化路径同样会产生 memcpy 记录。

## 本机（RTX 5060 8GB / 47GB RAM）的实测结构

```
step 2200ms（wall = gpu，gap = 0，GPU 确实在忙）

  Memcpy HtoD (Pinned -> Device)    834次  2136us  1780ms   <- 70%
  bt_gemv_bf16                      38次  8374us   318ms
  Memcpy HtoD (Pageable -> Device) 596次   484us   289ms
  fp8_gemv_inline_q                155次   639us    99ms
  moe_fused_act                     40次   263us    11ms
  moe_fused_down                    40次   136us     5ms
```

### 那 834 次 HtoD 是什么

240 次是专家装载（一步 40 层 x topk 6），其余是**按 tensor 逐个搬的层权重**。
层权重本该是一整块搬（slab 里每层一个连续块），只有 slab 装不下的层才退化成
逐 tensor —— 本机 slab 只装下 13/33 层，剩下 20 层每层 30 个 tensor，就是 600 次。

**这是当前最大的单项，约 1.2 秒/步。**

## 两个曾经走过的弯路（都很容易再踩）

### 1. 「看起来走了 pinned 路径」不等于走了

`torch.frombuffer(pool 的 memoryview)` 得到的 tensor，`is_pinned()` 返回 **False**，
即使那块内存确实来自 `cudaHostAlloc`。于是 `copy_()` 会先做一次 pageable memcpy
到内部 staging 再发 DMA —— 观测到的带宽只有 7.8GB/s，而 PCIe 的上限是 26GB/s。

判断方法只有一个：**加计数**。`_DMA_STATS` 就是为此加的。修之前它显示
`ok_calls=0, fallback=0` —— 一次都没走那条路，而代码看起来完全正常。

修法：直接对内存地址发 `cudaMemcpyAsync`（`_async_h2d`），绕开 torch 的 pinned 判断。

### 2. 宿主池不能吃满

「把可用内存全给池子」这个方向试过，会崩：

```
RuntimeError: !handles_.at(i) INTERNAL ASSERT FAILED
               (CUDACachingAllocator.cpp:487)
```

崩点是 `h.unsqueeze`、`dequant_fp8_block` 这类**运行期临时分配**，位置随机。
原因是池子是 pinned（锁物理页），吃干净之后 CUDA context、KV、activation、
dequant 中间量都没了空间。环境本身是健康的（物理可用 38GB、显存空闲 488MB）。

现在池子取可用量的 0.8。这个比例描述的是「池子与运行时的比例」，
不是「这台机器有多少内存」——后者才是那种换机器就静默失效的机器常数。

## 已知未解

slab 只装 13/33 层。根因是 `build_pool` 让 streamed 层权重先占一份 pool、
拷进 slab 又占一份，pool 被占两次。绕过 build_pool 之后 slab 确实能装到 33 层
（7.83GB，日志从 "partial slab 13/33" 变成 "33 layers, 7.3GB slab"），但池子
随之吃紧、撞上上面那个 allocator 问题。等池子配比调好之后这条值得重试 ——
它能消掉那 600 次逐 tensor 拷贝。

## 不要做的事

- **不要一次测量就下结论。** 这台机器上同一份代码的 step 在 2200~3100ms 之间
  波动（别的进程、页缓存温度、warm 线程进度都会影响）。至少跑 5 步取中位数，
  而且每组配置都要先预热到稳定（连续 3 步读盘量变化 < 10%）。
- **不要用「改一个参数、跑一次、回退」的方式调优。** 这类参数搜索属于训练器
  （`python -m tinyinfer.tune`），不是手工 A/B。
- **不要把「报告带宽低」当成硬件极限。** 先查是不是走了退化路径。
