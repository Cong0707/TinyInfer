# 为什么不做 pin（热点固定）：实测覆盖率

## 数据

64 个随机激活、单层（第 0 层），384 次路由：

```
碰到的不同专家 = 125 / 384

top-  6 -> 28.6% 的路由
top- 12 -> 40.6%
top- 24 -> 56.5%
top- 48 -> 74.7%
top- 96 -> 92.4%
```

## 这笔账

要覆盖 92% 的路由，每层需要 **96 个专家**。40 层 = **3840 个槽位**。

L20 只有 1359。8GB 卡只有 14-271。

**在预算内，pin 最多覆盖一半左右的路由** —— 另一半照旧要搬。而 pin 的代价是：

- 被 pin 的槽位永不淘汰，池子实际可用容量变小；
- 未命中的路由要在更小的池子里腾挪，命中率进一步下降。

这就是当年实测「pin 1119 个之后 decode 掉到 5.11 tok/s 且输出复读」的原因。**那个
结论是对的**，现在有了量化解释。

## 不走 pin，走什么

覆盖式槽位 + 局部性：

```
相邻激活重合 = 5/6        <- tests/test_route_locality.py
随机激活重合 = 2/6
```

槽位不 pin、不预留，纯靠「上一轮的 6 个专家大部分还在池里」自然命中。
相邻 token 重合 5/6 意味着稳态命中率能到 83% 左右，而**不需要**任何频率统计、
不需要 prefill 期的预热、不需要知道未来。

这也符合用户的原则：**不专门消耗算力去释放，按槽位覆盖**。pin 恰恰是反面 ——
它花力气管住一批槽位，收益却覆盖不到一半。

## 代码现状

- `pin_hot_experts` 还在（`engine.py`），但 `_all_pinned` 默认 False，
  即 pin 不参与 decode 的快速路径。`server.py` 启动时会调它，效果是
  「把热点先读进显存」—— 这在启动阶段是有用的（省掉前几步的冷启动搬运），
  但**不是**稳态策略。
- 真正的稳态策略是覆盖式槽位（`_claim_slot_locked` 的三轮优先级：别的层的 →
  本层已算完的 → 兜底）。
- 如果将来要重新考虑 pin，正确的形式是「按覆盖率目标反推预算」而不是
  「按频率排前 N 个」——前者才知道够不够。
