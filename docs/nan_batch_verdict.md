# MoE 多行路径：分批有 bug，不分批正确（2026-11-08 13:00）

## 决定性对照

**不分批**（`TI_MOE_BATCH >= 行数`）：

```
RESULT N= 8  bad=[]
RESULT N=11  bad=[]
RESULT N=12  bad=[]
RESULT N=16  bad=[]
RESULT N=20  bad=[]
```

全部正确，跨 5 个长度。

**分批**（默认 3）：

```
N=11  bad=[10]
N=8   bad=[6,7]
```

## 这意味着什么

MoE 的多行**分批逻辑本身有缺陷**，位置随批次大小移动，加任何 hook 就消失 ——
典型的数据竞争，但用打印法追不到（打印本身就是同步）。

## 两个选项的代价

| 配置 | 数值 | 8GB 卡长 prompt | L20 |
| --- | --- | --- | --- |
| 分批（默认 3）| **错** | 能跑 | 能跑（但结果错）|
| 不分批 | **对** | **OOM** | 能跑（1359 槽位够）|

分批的设计初衷：11 行 x 6 = 66 个专家请求，一批处理会让槽位池（14 个）
一次承受 66 个请求，反复覆盖；分 3 行一批降到 18 个。

## 已验证可用的配置

```powershell
$env:TI_MOE_BATCH = "64"    # 大于任何实际行数 = 不分批
```

在 8GB 卡上，配合 4-5 层的小模型，这个配置**数值正确**。

## 对目标场景（L20）的影响

L20 上槽位 1359 个，单批 66 个请求绰绰有余 —— **不需要分批**。
所以在这个问题上，L20 用 `TI_MOE_BATCH=64` 既正确又不会 OOM。

这反而说明：**分批是为 8GB 卡做的妥协**，而 8GB 不是目标机器。

## 仍未解决

分批路径的竞争。修它需要更系统的工具（CUDA memcheck / compute-sanitizer），
不能用打印法。留给有真卡的时候做。

## 建议的默认值改动（下一轮）

现在的默认 `TI_MOE_BATCH=3` 是错的（会产出 NaN）。应该改成：

```python
# 分批只在「槽位池装不下一次请求」时才启用
_need = rows * topk
_moe_bs = rows if slots >= _need else 3   # 或者更保守的算法
```

这样 L20 自动不分批（正确），8GB 自动分批（会错，但至少能跑 —— 需要修）。

**更好的做法**：分批时每批之间用双缓冲，不让任何 GPU buffer 跨批共享。
这是真正的修法，但需要系统性地重构 `_forward_gpu_only` 的 buffer 管理。
