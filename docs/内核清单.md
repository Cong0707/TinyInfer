# tinyinfer CUDA 内核契约清单（sm_120 消费级 Blackwell）

> 本清单只保留每个内核的**入参契约、几何约束、数值口径**，用于直接调用或重新实现时对照。
> 目标卡：RTX 5060 Laptop（sm_120，26 SM，8151 MiB）；单 block 动态 shared memory 上限 101,376 B（99 KB）。
> 误差口径：除注明外，「rel err」指对**同一量化数学的参考实现**的最大相对误差；bf16 舍入级的另注。

---

## 0 通用契约

### 0.1 格式记号

| 记号 | 含义 |
|---|---|
| FP8 | e4m3 |
| FP4 | E2M1，packed，两个值一字节，形状 [N, K/2] |
| e8m0 scale | 8 位指数 scale，只表示 2 的幂 |
| per-32 | 沿 K 每 32 个元素共用一个 scale（K 需为 32 的倍数） |
| 32×32 blockwise | 每 32 行（或 32 个输出通道）× 32 个 K 元素共用一个 scale |

- HF 非专家权重：FP8 e4m3 + 32×32 blockwise e8m0。
- HF routed expert 权重：FP4 E2M1 packed + 1×32 e8m0，与官方 `fp4_gemm` 的 B 侧一一对应，**不需要重排 scale**。
- 不要为了迁就别的 API 把上述布局改成 per-tensor，那会额外引入量化损失。

### 0.2 硬约束

- **shared memory**：单 block 动态 smem 上限 101,376 B。超过即启动失败，报 `Failed to set the allowed dynamic shared memory size`。
- **C 的 dtype**：`fp8_gemm` / `fp4_gemm` 的 C 必须是 bf16，且取自 `torch.get_default_dtype()`。调用前执行 `torch.set_default_dtype(torch.bfloat16)`，否则报 C dtype mismatch（官方在 `set_dtype()` 里全局设置）。
- **激活 dtype**：所有融合内核的激活入口都是 bf16 连续张量。
- **对齐**：per-32 scale ⇒ K 为 32 的倍数；FP4 packed ⇒ K 为偶数。
- **代码形态**：官方 pass_configs 关掉了 TMA，kernel 走 Ampere 风格拷贝（`mma` + float4/uint4 load），没有 warp-specialized。

### 0.3 M 分档（选 kernel 的第一判据）

| M | 走法 |
|---|---|
| M = 1（decode） | 反量化 bf16，或专用 GEMV；block_M=32 的 GEMM 会空转 31/32 行 |
| M ≥ 64 | prefill 走量化 GEMM；同一专家的多行要聚成 M ≥ 64 才吃满 tile |
| M ≥ 128 | FP8 GEMM 才明显快于 dequant + bf16；更小的 M 不划算 |

## 1 tilelang 官方 kernel

### 1.1 act_quant — 激活 FP8 量化

| 项 | 契约 |
|---|---|
| 入参 | x：bf16、连续、[M, N]，N 为 32 的倍数 |
| 出参 | e4m3 [M, N] + per-row per-32 e8m0 scale（每行每 32 个 K 一个） |
| 数值 | 最大绝对误差 = 该 block 的量化步长（[256, 5120] 上为 0.25） |
| 用途 | 替代 `.to(float8)` + 手工 scale；产物可直接作为 `fp8_gemm` / `fp4_gemm` 的 A |
| 限制 | 一次调用只量化一份激活；同一层 MoE 的 6 个专家应共用一次量化结果，不要每个专家各量化一遍 |

### 1.2 fp8_gemm — FP8 × FP8（32×32 blockwise）

| 项 | 契约 |
|---|---|
| 入参 | A：fp8 e4m3 [M, K]；B：fp8 e4m3 [N, K]（按行存，K 连续）；两侧均为 32×32 e8m0 block scale |
| 出参 | C：bf16 [M, N]（dtype 见 0.2） |
| tile | block_M=32、block_N=128、block_K=32；`mma` + float4/uint4，无 TMA |
| 数值 | 与该量化数学的参考实现一致，误差在 bf16 舍入级 |
| 限制 | M=1 时 31/32 行空转，比 dequant + bf16 慢；没有 warp-specialized / TMA，大 M 吞吐上不去 |

### 1.3 fp4_gemm — FP8 激活 × FP4 权重

| 项 | 契约 |
|---|---|
| A | fp8 e4m3 [M, K]，per-row per-32 e8m0 |
| B | fp4 E2M1 packed [N, K/2]，per-row per-32 e8m0 |
| C | bf16 [M, N] |
| 计算语义 | 先把 FP4 经 FP32 转成 FP8，再做 FP8 MMA，最后乘回 block scale —— **不是原生 FP4 MMA** |
| 格式兼容 | 与 HF routed_expert 的布局（E2M1 + 1×32 e8m0）完全一致，不需要重排 scale |
| 几何 | block_M=32，支持任意 M；K 为偶数；M ≤ 64 时 tile 效率低，prefill 应把同专家的行聚成 M ≥ 64 |
| 定位 | FLOPs 吞吐低于 `fp8_gemm`，但权重字节数减半；权重带宽受限的 decode 优先用它 |

### 1.4 hc_split_sinkhorn — HC 混合系数拆分

| 项 | 契约 |
|---|---|
| 入参 | mixes [M, 24]，fp32 |
| 出参 | pre [M, 4]、post [M, 4]、comb [M, 4, 4]，fp32（24 路 = pre 4 + post 4 + comb 4×4） |
| 参数 | 双随机归一化迭代 20 次 |
| 数值 | 对 tinyinfer Python 参考 max err 1.2e-7 |
| 限制 | 迭代次数不可省；pre/post 走 sigmoid、comb 走 softmax 且加 eps，顺序要与参考实现一致 |

### 1.5 sparse_attn（官方原版）—— 本卡不可用

| 项 | 契约 |
|---|---|
| 入参 | q / k / v：bf16，h=64 头、d=512；idxs [b, m, topk] |
| 失败原因 | `q_shared` + `o_shared` + `kv_shared` 按 64 头全量申请 141,312 B 动态 smem，超过 101,376 B 上限，启动即失败 |
| 结论 | 本卡不要直调，用 1.6 的 head 分块版 |

### 1.6 sparse_attn_sm120 — head 分块版

| 项 | 契约 |
|---|---|
| 与官方差异 | head 维切成 H_CHUNK=16 一组（grid 增加一维），KV tile = 32；smem 降到约 65 KB |
| 入参 | 同官方：bf16，d=512，idxs [b, m, topk]；idx 语义 = 每个 query 可见的窗口 slot + topk gather 位置 |
| 几何 | H_CHUNK 可按卡的 smem 余量调 8 / 16 / 32；block 32；99 KB 是硬上限 |
| 数值 | 对 naive gather 参考 max err 0.002–0.004（bf16 舍入级） |
| 覆盖形状 | decode 1 query × 640 KV；prefill 128 q × 640 KV；树形 verify m=4 / m=8（idxs 每行放自己的祖先链） |
| 前置 | 需 bf16 输入；sink 参与 softmax 归一化 |

## 2 融合 attention kernel

### 2.1 fused_rmsnorm_rope(N, rope_dim, eps)

| 项 | 契约 |
|---|---|
| 入参 | x [M, N] bf16；w [N] bf16；cos / sin [M, rope_dim/2] fp32 |
| 出参 | y [M, N] bf16 |
| 结构 | 一行一 block；行内 fp32 平方和 → `rsqrtf` → 乘权重；最后 rope_dim 维做表驱动旋转 |
| 退化 | rope_dim = 0 时等价于纯 RMSNorm |
| 约束 | rope_dim ≤ N 且为偶数；cos / sin 的行数必须等于 M（decode 传单行） |
| 数值 | 对参考 rel 4.8e-8（N=512、rope 64、128 行）；N=1280 rope=0/64 时与参考完全一致；max abs 1.95e-3 为 bf16 舍入 |

### 2.2 fused_gemm_rope(N, K, head_dim, rope_dim, block=32)

| 项 | 契约 |
|---|---|
| 入参 | A：fp8 [M, K]，32×32 e8m0 scale；B：fp8 [N, K]，32×32 e8m0 scale；cos / sin [M, rope_dim/2] fp32 |
| 出参 | C：bf16 [M, N] |
| 结构 | 官方 `fp8_gemm` 模板（block_M=32 / block_N=128 / block_K=32）+ RoPE epilogue：在每个 head 的最后一个 128 列 block 内旋转；C 先落 shared 再 `T.copy` 出去，以处理 M 边界 |
| 约束 | `head_dim % block_N == 0`；`rope_dim <= block_N`；RoPE 段必须落在每个 head 的最后一个列 block 内 |
| 数值 | 对 dequant + rope 参考 rel 1.9e-4（M=1、N=512、K=5120） |
| 限制 | M=1 时 block_M=32 浪费 31/32 行，收益主要来自 fp8 权重减半 + 省掉一次独立 RoPE launch |

### 2.3 rope_inplace(N, rope_dim, inverse, single)

| 项 | 契约 |
|---|---|
| 入参 | x [M, N] bf16 原地改写；cos / sin |
| 作用范围 | 固定最后 rope_dim 列 |
| inverse | 取共轭（反向旋转） |
| single | `single=True` 时 cos / sin 只给 1 行（decode 复用），避免 repeat / copy |
| 数值 | 融合版整层对照 torch 同 fp8 数学参考 rel 0.0（bf16 舍入以内） |

## 3 融合 Hyper-Connections kernel

### 3.1 fused_hc_mixes(HD, mix, eps)

| 项 | 契约 |
|---|---|
| 入参 | x [M, HD] bf16，HD = hc × D = 20480；hc_fn [24, HD] fp32 |
| 出参 | mixes [M, 24] fp32 |
| 结构 | 一行一 block；shared 存 x（40 KB）；行内 fp32 平方和 → rsqrt；24 个输出各自做一次 reduce_sum |
| 约束 | HD 必须等于 hc × D（hc=4、D=5120）；shared 用量随 HD 线性涨 |
| 限制 | 每行都要读 24 × HD fp32 = 1.97 MB 的 hc_fn；M=1 就是一次 2 MB 读；prefill M>1 按行重复读（靠 L2 缓解），当前只为 decode 调优 |

### 3.2 fused_sinkhorn(hc, iters, eps)

| 项 | 契约 |
|---|---|
| 入参 | mixes [M, 24] fp32；scale [3]；base [24] |
| 出参 | pre [M, 4]、post [M, 4]、comb [M, 4, 4]，fp32 |
| 结构 | 一行一 block、64 线程；仿射 → sigmoid 得 pre/post、softmax + eps 得 comb；双随机归一化在 kernel 内串行，row_sum / col_sum 用 fragment reduce，迭代顺序与参考 `hc.py` 一致 |
| 约束 | iters 不能压：iters=6 相对 20 次的 comb 偏差 15.6%（pre/post 不变），默认按 20 次 |

### 3.3 fused_hc_pre(D, hc)

| 项 | 契约 |
|---|---|
| 入参 | x [M, hc, D] bf16；pre [M, hc] fp32 |
| 出参 | [M, D] bf16 |
| 结构 | shared 存 hc × D，hc 次加权求和 |
| 数值 | 对参考 rel 0 |

### 3.4 fused_hc_post(D, hc)

| 项 | 契约 |
|---|---|
| 入参 | x [M, D] bf16；residual [M, hc, D] bf16；post；comb |
| 出参 | [M, hc, D] bf16 |
| 结构 | shared 存 x + residual |
| **索引口径** | `out[h] = post[h] * x + Σ_h2 comb[h2, h] * res[h2]` —— comb 的**第一维是被求和的轴**（官方广播语义）。按 `comb[h, h2]` 写会得到相反的顺序（rel 0.26），改对后归零 |
| 数值 | pre / post / hc_pre / hc_post 对参考 rel 0；comb rel 6.3e-8 |

## 4 decode 专用 fp8 GEMV（M = 1）

| kernel | 入参 | 线程布局 | 适用 |
|---|---|---|---|
| `gemv_bf16_kernel` | x bf16 [K]（未量化）、w fp8 [N, K]、ws e8m0 | 每 block 先做一次激活 32-block 量化到 shared（Aq / As），再 rows=8 行 × 32 lane，每线程一个 (row, lane)，K 串行累加 | 入口是 bf16 激活，省一次 `act_quant` launch |
| `gemv_pq_kernel` | Aq fp8 [K]、As [K/32]、w、ws | rows=16，线程 = rows × 32；可选 RoPE epilogue | 激活已预量化（推荐） |
| `gemv_pq4_kernel` | 同上 | 每线程 4 个连续 k（lanes=8 每行，rows=64），减少循环次数 | K 小（如 1280）时最快；K 大（8192）时 4-FMA/迭代不划算 |

| 项 | 契约 |
|---|---|
| 数值 | rel 1.35e-3–1.41e-3（对同一量化数学的 dequant 参考）；带 RoPE epilogue 的 wq_b / wkv 为 1.40e-3 / 1.32e-3 |
| 线程上限 | 32 lane × rows=64 会超过 1024 线程上限，直接编译失败 |
| 访存 | 权重只读一遍，每 warp 每迭代 32 B sector 交易，未用 16 B 向量 load |
| 物理下界 | wq_b / wo_b 权重 41.9 MB，本卡实测有效带宽 338 GB/s ⇒ 下界约 124 µs；要到 60 µs 需 > 700 GB/s，超出该卡 HBM 能力 |
| 选型（M=1） | wq_a / wkv / wo_b 走 bf16 入口；wq_b 先 `act_quant` 再 pq4；wkv 之后接 `fused_rmsnorm_rope`；wq_b 直接带 RoPE |

## 5 MoE 融合 kernel（fp4 专家）

| kernel | 语义 | 契约 |
|---|---|---|
| `fused_fp4_swiglu_pq` | gate = A@W1ᵀ、up = A@W3ᵀ，同一 kernel 内做两次 fp4 GEMM（共享 A 及其量化）→ clamp → silu(gate)*up → h [M, 2304] bf16 | A 必须预量化；epilogue 必须先把 gate / up round 到 bf16，再 clamp / silu |
| `fused_fp4_down_pq` | y = (A@W2ᵀ) × weights[:, None] → [M, 5120] bf16 | A = h，需预先 `act_quant`；weights 为每 token 的路由权重 [M] |
| `fused_fp4_expert_ffn` | act_quant(x) → swiglu → act_quant(h) → down | 每专家 4 个 kernel（2 次 `act_quant` + 2 个 tilelang） |
| `fused_fp4_swiglu` / `fused_fp4_down` | bf16 入口、内部自带量化 | 每个 N block 重复量化 A，慢得多；仅作 API / 对照，不要接生产 |

| 项 | 契约 |
|---|---|
| 权重形状 | W1 / W3 [2304, 5120]、W2 [5120, 2304]，fp4 packed + 1×32 e8m0 |
| tile | M=8 用 block_M=16 / block_N=64；M=64 用 block_M=64 / block_N=128 |
| 数值（关键） | epilogue 先 round 到 bf16 再 clamp / silu。直接用 fp32 累加器做 silu 会让 h 差 0.2%，经后续 act_quant 放大约 1.4e-2；round 后 rel 1.91e-3–1.97e-3（M=8 / 64，对官方 `fp4_gemm` + torch 逐元素参考） |
| 拆分限制 | down 需要完整 h 行（2304），必须跨 block 同步，所以单专家单 kernel 做不到；只能在外部 `act_quant` 之后拆成两个 kernel |

## 6 数值口径：精确 / 硬件 intrinsic / 多项式近似

- 三种实现：exact = `T.exp`（expf）/ `T.rsqrt`；hw = `T.__exp`（硬件 intrinsic）；poly = bit-trick rsqrt + Newton、多项式 exp。
- **结论：GPU 侧默认关闭近似，只用硬件 intrinsic。** sm_120 上 softmax / attention 都是 memory-bound，exp 占比 < 5%；`rsqrtf` 是单条硬件指令，bit-trick + Newton 反而多几条 FMA。

| 近似 | 精度（真实 L0 权重，对精确实现） |
|---|---|
| fast_rsqrt（RMSNorm） | attention 输出 rel 0.449%（1 次 Newton） |
| fast_exp（attention softmax） | 输出 rel 0.191%；注意力权重 KL 3.18e-5；top1 100% |
| fast_silu（SwiGLU） | 中间 rel 4.8e-4，expert 输出 rel 0.158% |
| poly exp（LM softmax） | KL 1.1e-6；top1 100% |

- RoPE 预计算 sin / cos 表：与 torch complex 路径数值一致（bf16 舍入级），是这一类里唯一确定有收益的 kernel。
- 近似只在 CPU 路径有意义（AVX512 向量化的 Arm 算法），GPU 侧多项式只带来精度损失。

## 7 KV 量化格式口径（512 维 MLA latent）

| 方案 | bytes/val | 平均相对误差 | cosine |
|---|---:|---:|---:|
| FP8 e4m3 per-32 e8m0（窗口 KV） | 1.0 | 2.25% | 0.99965 |
| FP4 E2M1 per-16 e4m3（压缩 KV） | 0.5 | 10.3% | 0.99569 |
| int8 per-32 | 1.0 | 0.97% | 0.99996 |
| int8 + Hadamard per-32 | 1.0 | 0.60% | 0.99999 |
| int4 per-32 | 0.5 | 17.5% | 0.98598 |
| int4 + Hadamard per-32 | 0.5 | 10.9% | 0.99629 |

- 写侧口径：窗口 KV 用 FP8 per-32、压缩 KV 用 FP4 per-16，与模型训练一致；用 `act_quant` / `fp4_quant` 在写 cache 时直接量化。
- Hadamard 对 int4 提升明显（17.5% → 10.9%），int8 + Hadamard 精度最好但没有压缩收益。

## 8 torch._scaled_mm 的契约与禁区

| 路径 | 入参契约 | 可用性 |
|---|---|---|
| tensorwise FP8（e4m3） | per-tensor scale，需把权重重新按 per-tensor 量化 | 可用；但与 HF 的 32×32 布局不兼容，重量化有精度损失 |
| rowwise FP8 | per-row scale | 被设备拒绝，sm_120 不可用 |
| blockwise 1×128 / 128×128 | — | stride 校验不通过，起不来 |
| MXFP8 e8m0 blockwise | e8m0 block scale | 能启动，但 scale layout 无公开文档，结果错误，不可依赖 |
| NVFP4（fp4 × fp4） | 见下 | 能跑，但 scale 布局未解，只作研究 |

NVFP4 的具体契约：

- 调用形态：`torch._scaled_mm(a_packed[M, K/2], b_packed[N, K/2].t(), sa, sb, out_dtype=bf16)`。
- dtype：a / b 均为 `torch.float4_e2m1fn_x2`，scale 为 `float8_e4m3fn`，粒度 per-16。
- scale 尺寸（从 C++ 报错反推）：`scale_a.numel() == 128 * ceil(M/128) * (K/16)`、`scale_b.numel() == 128 * ceil(N/128) * (K/16)`，且都必须 contiguous。
- 数值：单位 scale 时与手工 dequant 完全一致（code → E2M1 映射、packed 顺序已用常量矩阵核对）；一旦换成真实 per-16 e4m3 scale，误差达 50%–100% —— scale 张量的 swizzle / 索引布局没有公开文档，torch 也没有公开 helper。
- 精度口径：它是 W4A4（激活也走 FP4）。实测 w4a4 单次乘积误差 8.6%、KL 0.008，远差于 w4a8 的 0.53%、KL 0.0018。
- 结论：不作为主路径。

**原生 FP4 MMA 的 arch 前提**：FP4 × FP4 的 MMA 必须用 `sm_120a` 目标编译，其余引擎按普通 arch 编译并在没有该编译单元的卡上回退 w4a8。tilelang 默认按 `torch.cuda.get_device_capability()` 生成 `sm_120`；要启用原生 FP4 MMA 需把 target 改成 `sm_120a`（tilelang 0.1.15 是否接受未验证）。26 SM 这一档卡也不在默认启用 w4a4 的范围内。

## 9 按张量分流的调用规则

| 张量 | 形状 (N × K) | M = 1（decode） | M ≥ 64（prefill） |
|---|---|---|---|
| attention wq_a / wkv / wo_b | 1280×5120 / 512×5120 / 5120×8192 | 反量化 bf16 或 `gemv_bf16_kernel` | `fp8_gemm` |
| attention wq_b | 32768×1280 | bf16（大 N 小 K，fp8 GEMM 在 M=1 反而更慢）；GEMV 走 pq4 | `fp8_gemm` |
| attention wo_a（分组 block-diagonal） | 8×(1024×4096) | bf16 einsum | bf16 einsum（拆 8 次小 GEMM 不划算） |
| shared expert w1 / w2 / w3（fp8） | 2304×5120 等 | bf16 | `fp8_gemm` |
| routed expert w1 / w2 / w3（fp4） | 2304×5120 / 5120×2304 | `fp4_gemm` 或 `fused_fp4_expert_ffn`（权重流式时 IO 减半） | `fp4_gemm`，同专家行聚成 M ≥ 64 |
| gate（fp32） | 384×5120 | GPU 或 CPU 均可（可提前一层算） | GPU |

实现要点：

1. **激活只量化一次，复用 6 次**：MoE 一层的 6 个专家应共用同一份 `x [M, 5120]` 的 `x_fp8, x_scale`，传给 6 次 `fp4_gemm`，而不是每次 linear 内部各量化一遍。
2. **M 阈值以 0.3 为准**：fp8 在 M ≥ 128 才有稳定收益；decode 一律反量化 / bf16（wq_b 走 fp8 反而慢）。expert fp4 即使 M=1 也该用（权重流式时 IO 减半），但权重已常驻 bf16 时 M ≤ 8 用 bf16 更快。
3. **权重驻留**：非专家 fp8 常驻内存，GPU 上只放当前层的副本；专家按需预取，不常驻。
4. **精度**：保持 HF 的 32×32（非专家）/ 1×32（专家）scale 布局，不要为了用 torch tensorwise 而 requantize。
5. **验证**：接入后用真实 L0 分片的 dequant 对照做端到端 logits 比对；fp8 / fp4 本身的量化误差在 1.5% / 2.4% 量级。

## 10 编译与缓存前提（tilelang）

- 依赖：tilelang 0.1.15 + nvcc 13.0 + VS2022 BuildTools 的 `cl.exe`（`vcvars64.bat` 环境）。**不需要 clang / MSYS2。**
- JIT 必须在 vcvars64 环境里跑：nvcc 需要 `cl.exe` 做 host 编译，否则报 host compiler 错误。
- 编译粒度：按 (kernel, shape, M) 组合独立编译，未缓存的组合首次调用约 5 s；改 tile 参数（H_CHUNK、block_M / block_N）或换卡同样要重新编译。
- 缓存位置：`~/.tilelang/cache/0.1.15/cuda-binaries/<hash>/kernel.cubin`，之后启动只做加载。
- 部署：把编译好的缓存随镜像发布（或 bootstrap 跑一次），否则冷启动是分钟级。

## 11 明确不要做的事

- 直调官方 `sparse_attn`：141 KB smem 超过本卡 101,376 B 上限。
- 依赖 rowwise FP8、1×128 / 128×128 blockwise、MXFP8 e8m0：分别是被拒、校验失败、布局无文档。
- 把 torch NVFP4 当主路径：scale 布局未解 + W4A4 精度风险。
- 为了迁就 torch tensorwise 而改写 HF 的 32×32 / 1×32 scale 布局。
- 在 sm_120 + D=512 上试 SDPA 的 flash / efficient / cuDNN 后端：无可用 kernel，只剩 math 路径。
- 用 CPU 承担主专家计算（会把 IO-bound 变成 CPU-bound）。
- 没把 target 改成 `sm_120a` 就指望原生 FP4 MMA。
