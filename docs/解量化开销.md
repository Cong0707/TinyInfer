# 一个隐藏的解量化开销：wo_a 是 fp8，计算前先变成 bf16

## 现象

profile 里 `bt_gemv_bf16` 38 次共 318ms（每步第二大开销）。但单独测这个 kernel
只要 10~20us —— 差了 500 倍。

## 原因

`attn.wo_a.weight` 的真实形状和类型：

```
  wo_a: shape=(8192, 4096) dtype=torch.float8_e4m3fn contiguous=True
```

**它是 fp8（33.5MB），不是 bf16。** 而 `bt_gemv` 那条快路径的判据是
`wo_a.dtype == torch.bfloat16`，所以它先走：

```
  wo_a = dequant_fp8_block(self.wo_a.weight, self.wo_a.scale)   # fp8 -> bf16，67MB
  ... 然后才进 bt_gemv
```

于是每层的真实开销是「解量化 33.5MB fp8 -> 67MB bf16」+「在 bf16 上做 GEMV」，
而 profiler 把它归到 `bt_gemv_bf16` 名下，看起来像是 GEMV 本身慢。

## 为什么值得记下来

两个可能的优化方向，但都需要改内核、不是调参：

1. **直接在 fp8 上做 GEMV**（累加时按 block scale 还原），省掉中间那 67MB 的
   bf16 张量和一次完整的读写。这是 vLLM/TRT-LLM 的标准做法。
2. 至少把解量化结果缓存起来 —— 但 wo_a 是 streamed 权重、每步都变，缓存不了，
   除非 slab 覆盖到那一层（又是一个「slab 装不装得下」的问题）。

## 顺带确认的事

`wo_a.reshape(-1).contiguous()` 是 **no-op**（源本来就连续，data_ptr 不变），
所以那不是开销所在 —— 我一开始怀疑错了。真正的开销是上一步的 dequant。
