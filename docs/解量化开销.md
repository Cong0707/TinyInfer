# 一个隐藏的解量化开销：wo_a 是 fp8，计算前先变成 bf16

## 现象

profile 里 `bt_gemv_bf16` 38 次共 318ms（每步第二大开销）。但单独测这个 kernel
只要 10~20us —— 差了 500 倍。

## 原因

`attn.wo_a.weight` 的真实形状和类型：

```
  wo_a: shape=(8192, 4096) dtype=torch.float8_e4m3fn contiguous=True
```

**它是 fp8（33.5MB），不是 bf16。** 而 `bt_gemv` 那条快路径的判据是
`wo_a.dtype == torch.bfloat16`，所以它先走：

```
  wo_a = dequant_fp8_block(self.wo_a.weight, self.wo_a.scale)   # fp8 -> bf16，67MB
  ... 然后才进 bt_gemv
```

于是每层的真实开销是「解量化 33.5MB fp8 -> 67MB bf16」+「在 bf16 上做 GEMV」，
而 profiler 把它归到 `bt_gemv_bf16` 名下，看起来像是 GEMV 本身慢。

## 为什么值得记下来

两个可能的优化方向，但都需要改内核、不是调参：

1. **直接在 fp8 上做 GEMV**（累加时按 block scale 还原），省掉中间那 67MB 的
   bf16 张量和一次完整的读写。这是 vLLM/TRT-LLM 的标准做法。
2. 至少把解量化结果缓存起来 —— 但 wo_a 是 streamed 权重、每步都变，缓存不了，
   除非 slab 覆盖到那一层（又是一个「slab 装不装得下」的问题）。

## 顺带确认的事

`wo_a.reshape(-1).contiguous()` 是 **no-op**（源本来就连续，data_ptr 不变），
所以那不是开销所在 —— 我一开始怀疑错了。真正的开销是上一步的 dequant。
## 补记：两条解量化路径的数值差异

`dequant_fp8_block` 有两条路径：CUDA 快路径（tilelang 融合内核）和 torch 兜底
（fp8 -> fp32 -> 乘 scale -> bf16，中间张量 134MB）。

实测同一个 wo_a（[8192,4096] fp8，scale [256,128] e8m0）：

```
  fast : (8192, 4096) bf16
  torch: (8192, 4096) bf16
  max_diff  = 2.344e-01
  mean_diff = 2.148e-02
```

**2% 的权重误差。** 这个量级本身可能只是 bf16 舍入顺序不同（fp32 乘加后各自
舍入到 bf16），但如果拿它做完整 forward，logits 的变化会很大 —— 实测同一段
输入、同样 5 个 token，两种路径下 top-1 logit 分别是 12.6 和 18.8。

原因不是「哪个算错了」，而是 **wo_a 有 4096 个输入维度**：每个元素的 2% 相对
误差在累加时按 sqrt(N) 量级合成，再经过 40 层传播，输出尺度的差异被放大到
几十个百分点是合理的。

### 这意味着什么

1. **不能拿两种路径的 logits 互相对比来判断对错** —— 必须先确定基准。
   判断依据应该是「哪条路径更接近 bf16 参考实现」，而不是「哪个数看起来正常」。
2. 快路径存在与否取决于当时的显存状态（之前日志里见过
   `dequant fast path unavailable (cuMemSetAccess OOM); using torch`），
   所以**同一个模型在不同启动条件下可能给出不同的 logits**。如果要复现某个
   输出，必须固定走哪条路径。
3. 这条还没查透：两条路径哪个是基准、差异是否在可接受范围，需要拿一份
   官方参考输出（或 fp32/bf16 全精度实现）对齐才能下结论。在那之前不要
   基于「换一条路径更快」做优化。
