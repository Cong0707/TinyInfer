## 这一轮修掉的根因

`MoE._last_ids` 从来没有被赋过值 —— 那份赋值被缩进进了 `TI_GPUDBG == "1"` 的调试块里，
所以 `release()` 一次都没被调用过。后果是槽位的 `refs` 只增不减：

- 1359 个槽位全部卡在 `IN_USE`、`refs > 0`、`evictions == 0`；
- `_find_victim_locked()` 一个可回收槽位都找不到 → `acquire()` 返回 `-1`；
- kernel 用 `slot_ids[e] * blob_bytes` 寻址，`-1` 就是 `INT_MAX * 18.8MB` 的偏移 ——
  算出来的数值是垃圾，表现是乱码和 `still not resident`。

现在 `_last_ids` 在 `MoE.forward` 里无条件设置，每层 forward 结束后 `release()` 把
refs 减到 0（state 转 STAGED，数据留着，下一步命中最快）。

顺带修掉的两个正确性问题：

- `_evict_locked()` 不清 device 上的槽位表 —— 槽位被别的专家复用时，表中还留着旧编号，
  下一层路由到同一专家会静默读到别人的权重。现在 evict 一律把表置 -1。
- DMA 覆盖一个刚被收回的槽位时，可能盖掉还在被 kernel 读的显存。现在 evict 时在该槽位上
  记一个 compute stream 事件，`_copy_blocking()` 覆盖前 `wait_event` 它（只有被回收过的
  槽位才插这个同步点，用 `_dirty` 字典分开记）。

## 速度为什么掉下来（明天从这里开始）

这一轮的修法有两个地方是「每层都做」的：每层 `release` + 每层按需 evict + 每层一个
事件对象。decode 稳态只需 40 × topk = 240 个槽位，而池子有 1359 个 —— 本来可以全程
零 evict、零重读，现在却每步每层都在腾位置、都在等事件，异步流水线被拉成串行。

（`942125b` 已经把「只在池子用掉 75% 以上才回收本层旧槽位」加上去了，速度没有变化，
说明真正的开销还在别处 —— 大概率是 `_miss_scan()` 的每层同步点，以及每层 `_evict_locked`
里的表赋值。下一步先量，不要先改。）

## 下一步：统一的存储层级管理器

现在的槽位、RAM 缓存、磁盘读取分散在三处：`loading.VramSlotCache`（显存槽位）、
`loading.ExpertStore`（RAM 缓存/pinned 池）、`loading.ShardStore`（磁盘分片）。
每加一个功能就要在 `moe.py` 里补一遍回收逻辑，所以修一处崩一处。

目标是一个对象负责整条链路：

1. GPU 侧只判断「我这层缺哪几个专家」（`moe_miss_scan` 已经能出缺失表），
   不把整条 `sids` 拉回 CPU；
2. 管理器收到缺失表，按「显存 → 内存 → 磁盘」逐级取：显存在就直接指槽位，
   在内存就下一笔 DMA，都没有才让 CPU 去盘上读；
3. 搬运动作是异步的，GPU 继续算别的层，等到用之前再 wait 那一个事件；
4. 回收、pin、并发请求的合批，全部由管理器统一决策，`moe.py` 里不再出现
   `_by_key` / `_evict_locked` / 手工清表这些内部细节。

并发（多请求同时在飞）是这个管理器的另一个输入维度：一次前向的专家集合是
「所有在飞请求的并集」，释放时机是「所有请求都不再需要它」，而不是「本层算完」。
