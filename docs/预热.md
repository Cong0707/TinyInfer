# 预热：一个被忽略的变量

这份文件记录一个会让人误判性能的因素：**预热到什么程度，决定你测出什么数。**

## 同一份代码，三个数量级不同的数字

```
  探针（3-token 上下文，预热到连续 3 步读盘量变化 < 10%，约 30 步）
    step = 2086ms   (0.479 tok/s)   极差 51ms / 2.4%

  bench（完整 prompt，预热判据跑到上限 80 步）
    decode_steady = 0.196 tok/s     (约 5100ms/步)

  不预热（跑几步就测）
    2083 / 4060 / 3671ms            极差 2 倍
```

**三个都是真的。** 差别在于系统当时处在什么状态：

- 后台 warm 线程还在往 RAM 里装专家 → 读盘量大、decode 被 IO 挤占
- 专家缓存命中率随之变化（bench 那次是 59%）
- 预热跑得越久，读盘累计越多（bench 那轮累计读了 234 GB）

## 怎么比较两个配置

1. **两边必须用同一个预热判据。** 用「连续 3 步读盘量变化 < 10%」而不是固定
   步数 —— 不同配置需要的预热步数不一样（本机 20~80 步），固定步数会让
   「预热慢的那个」看起来更差。
2. **报中位数和极差，不报单次。** 预热充分时极差能到 2.4%（2086±25ms），
   预热不足时能到 100%。
3. **说清是哪个场景。** 3-token 上下文和完整 prompt 的稳态本来就不同 ——
   但要注意：**decode 本身对上下文长度并不敏感**（实测 ctx=8/128/512 分别是
   2148/2123/2197ms），所以「长上下文更慢」不成立，慢的是预热和缓存状态。

## 预热上限要留个记录

bench 的预热判据没在 80 步内满足时会跑满 80 步，读 160GB 盘。这本身成了
一次压力测试，测出的稳态和「预热 30 步就停」不是同一个状态。**如果发现
bench 比探针慢一倍，先看预热跑了多少步。**
