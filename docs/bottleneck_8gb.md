# 8GB 卡上的真实瓶颈（2026-11-08 实测）

结论只有一句：**计算不是瓶颈，专家搬运是。**

## 数据

### 单层完整 block（attention + MoE + 超连接）

| 场景 | 单层 | ×40 |
| --- | --- | --- |
| 专家已驻留槽位（路由固定） | 1.9 - 2.2 ms | 76 - 88 ms |
| 真实 decode（每 token 路由都变，专家要搬） | **80 ms** | **3.2 s** |

同一个 block，差 40 倍。差的全部是「等 6 个专家到槽位」。

### 一个真实 decode step（12 层，TI_SLOTS=14）

```
STEP_TOTAL_MS 1031
  layer  0  69.29 ms
  layer  1  67.30 ms
  ...
  layer 11  81.17 ms
SUM_BLOCK_MS 989.9   UNACCOUNTED 41
```

没有未解释的空白：99.6% 的时间在层内部的 forward 里，而层内部 97% 在等专家。
`_flat_apply`（层权重 streaming 的 CPU 提交）整步只调用 1 次、0ms —— 层权重不是瓶颈。

### 槽位数的硬约束

本机（RTX 5060 Laptop，8GB）能加载的组合：

| n_layers | slots | 结果 |
| --- | --- | --- |
| 12 | 14 | OK 单层 2.2ms |
| 12 | 32 / 64 | OOM |
| 40 | 14 / 32 / 64 | OOM |

40 层 x 6 专家 = 240 个槽位才够稳态全命中，8GB 卡给不出（240 x 18.8MB = 4.5GB，
已经超过整卡可用显存的一半，还没算层权重、KV、激活）。

**所以 8GB 卡的物理上限就是「每步重读大部分专家」，1 tok/s 量级是这个硬件的
真实结果，不是软件缺陷。** L20（44GB，1359 槽位）装得下 240 + 层权重，那里才谈得上优化。

## 已经做掉的事

1. **槽位池改成覆盖式**：空槽 LIFO + 环形游标，没有独立的释放动作。每层遍历
   1359 个槽位找 victim 的 Python 循环换成了摊还 O(1) 的游标。
   `tests/test_slot_pool.py` 5 条不变量。

2. **槽位表由池子自己维护**：以前散在 `moe.py` 的 `table_set` / 手工清表里，
   漏一处就是「kernel 读到别人的权重」这种不报错的错误。现在 `_reserve_locked`
   记账 + `table_flush()` 一次刷。

3. **删掉每层「还槽位」**：小卡按「装不下整步」判断，每层把整层专家扔回池子，
   每 token 重读 4.5GB。实测单层 5 次前向 `loads=6 evict=0`。

4. **`ExpertTierManager`**：显存 / 内存 / 磁盘收成一个对象，MoE 只说 `need`。
   `tests/test_expert_tiers.py` 锁住三级顺序。

5. **`DerivedCache`**：可重算的显存（`wo_a` 反量化 64MB x 40 层 = 2.5GB）改成
   容量驱动的 LRU。小卡转得快，大卡一次装下。

6. **滚动预取**：算第 k 层时把第 k+1 层的专家搬进槽位。`urgent=False` 保证它
   只填空槽，绝不和当前层抢（否则当前层自己都装不进去）。

## 下一步（在 L20 上做，本机做不了）

- 240 个槽位 + 余量 = 1359，稳态应该做到**零 evict、零重读**。在那之前先量：
  `slot loads / (decode steps x 40 x 6)` 就是重读率，目标是 0。
- 预取在那台机器上才有意义：8GB 上槽位全满，预取抢不到空位
  （实测 1067ms vs 没有预取的 1031ms，一样）。
- `_mgr.commit()` + `_miss_scan` 仍是每层一次主机同步。真正的零同步要「延迟一拍」：
  第 k 层的缺失在第 k+1 层提交。这需要先有稳态零缺失。
- 并发与 1M 上下文：KV 分层（显存 / 内存 / 盘）还没开始。
