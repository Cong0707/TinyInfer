# 本轮实测结论（更新）

## 已定位并修掉的一个真实浪费

`pool.stage()` 对每个 18.8MB 的专家做了一次主机 memcpy（拷进中转 bytearray），
而 RAM 缓存里的字节本来就是 pinned 的 memoryview，DMA 可以直接读它。

| 指标 | 修前 | 修后 |
| --- | --- | --- |
| `stage` 每步 | 175 ms | **3.8 ms** |
| 整步（8 层） | 499 ms | **276 ms** |

单层从 62ms 降到 34ms。这是一次纯粹的浪费，不是算法问题。

## 分解清楚了（8 层，`TI_SLOTS=14`，RAM 命中 100%）

```
STEP 276ms
  stage  = 4.9ms   (48 个专家挑槽位 + 记录)
  commit = 143ms   (48 次 DMA，每次 1.5-2.6ms)
  MoE kernel + attention ≈ 124ms
```

- RAM 缓存命中率 **100%**（`misses=0`, `disk_reads=0`）：不读盘，不是 IO 问题。
- `miss_scan` 每层 0.14ms、`gate` 每层 0.14ms：不是同步问题。
- attention 只有 15ms/8 层：不是 attention 问题。
- MoE 的 host 时间 ≈ CUDA 时间（559ms vs 558ms）：GPU 真的在跑，CPU 没在空等。

## 真正的约束：槽位数

`slot loads=768 evict=754 hits=0`（8 层一步）。槽位从未命中，因为：

- 8 层 × 6 = 48 个专家/步，池子只有 14 个；
- 每个专家搬进来立刻被下一个顶掉，**必然 100% miss**。

这不是策略问题（urgent 优先级已经实现：当前层不许被别的层顶掉），是**物理容量**：
48 × 18.8MB = 902MB，而 8GB 卡扣掉模型、KV、激活之后给不出这么多连续的槽位。

## 单次 DMA 的硬件速度（本机实测）

- 单个 18.8MB blob：**2.65ms = 7.11 GB/s**（`cudaHostAlloc` pinned → VRAM）
- 14 个连续发：37ms（2.65ms each，无额外开销）
- Event 记录开销：**0**（36.9ms vs 37.1ms）

所以 48 个专家/步的下限是 48 × 2.65 = **127ms**，实测 commit 143ms —— **已经接近硬件下限**。

## 结论

8GB 卡上，decode 的物理下限 = 每步搬 48 个专家 ≈ 127ms + 计算 124ms ≈ **250ms/步 = 4 tok/s**。
实测 276ms，**已经在这个下限附近**。

要再快只有两条路：
1. **减少每步要搬的专家数** —— 只能靠更大的槽位池（L20 的 1359 个装得下 240，稳态 miss=0）；
2. **提高 DMA 带宽** —— 7.11GB/s 是这块笔记本卡 PCIe 的实际上限。

L20 的 PCIe 4.0 x16 是 25GB/s，同样 48 个专家只要 36ms；而且 1359 槽位能装下全部 240，
稳态根本不搬。**那台机器上这套代码应该直接跑到 6-10 tok/s 以上，而不是 1 tok/s。**
