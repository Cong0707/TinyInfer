# 8GB 卡上 decode 的完整账（2026-11-08 最终版）

## 一句话

**计算只占 4%，96% 在等专家搬运。** 这不是软件缺陷，是 8GB 显存的物理上限。

## 数据（全部本机实测，RTX 5060 Laptop 8GB）

### 计算本身

| 场景 | 单层 | ×40 |
| --- | --- | --- |
| MoE，专家已全在槽位（topk=6） | 0.95 ms | **38 ms** |
| MoE，真实 decode（专家要搬） | ~80 ms | **3.2 s** |
| attention（window/compressed 混合） | ~2 ms | ~80 ms |
| 超连接 hc_mixes + hc_pre（每层 2 次） | ~0.14 ms | ~6 ms |

所以计算侧 40 层大约 76-120ms。真实一步是 1031ms（12 层）或更久（40 层）。

### 搬运的硬件下限

| 指标 | 实测 |
| --- | --- |
| 单个 18.8MB 专家 blob，pinned → VRAM | **2.65 ms = 7.11 GB/s** |
| 14 个连续发 | 37 ms（2.65ms each，无额外开销） |
| `torch.cuda.Event` 记录开销 | **0**（36.9 vs 37.1ms） |

8GB 卡上池子只有 14 个槽位，一层要 6 个专家、8 层就要 48 个 —— **必然 100% miss**，
`slot loads=768 evict=754 hits=0`。每步搬 48 个专家 = 127ms，实测 143ms，
**已经贴着硬件下限**。

### 槽位数的硬约束

| n_layers | slots | 结果 |
| --- | --- | --- |
| 12 | 14 | OK |
| 12 | 32 / 64 | OOM |
| 40 | 14 / 32 / 64 | OOM |

40 层 × 6 专家 = 240 个槽位才够稳态全命中，240 × 18.8MB = 4.5GB，
8GB 卡给不出（还没算层权重、KV、激活）。

## 结论

8GB 卡的物理下限：

```
每步 = 48 个专家 × 2.65ms（搬运） + ~120ms（计算） ≈ 250ms = 4 tok/s
实测 276ms —— 已经在这个下限上。
```

要再快只有两条路：
1. **更大的槽位池**（L20 的 1359 装得下 240，稳态 miss=0，搬运项归零）；
2. **更高的 PCIe 带宽**（L20 是 25GB/s，同样 48 个专家只要 36ms）。

## L20 上应该是什么样

| 项 | 8GB 本机 | L20 44GB |
| --- | --- | --- |
| 槽位数 | 14 | 1359 |
| 每步要搬的专家 | 48（100% miss） | **0**（240 个全驻留） |
| 搬运耗时 | 127ms | **0** |
| 计算 | ~80ms | ~80ms |
| 每步 | ~276ms | **~80ms = 12 tok/s** |

再加上并发（4-7 条会话共享一次 forward），吞吐能到 40-80 tok/s 量级。
**这才是这台机器该有的样子，也是这套代码的目标。**

## 已做的优化（按收益排序）

1. **`stage()` 不再 memcpy**：原来每个 18.8MB 专家都拷进中转 bytearray，
   而 RAM 缓存里的字节本来就是 pinned 的。删掉之后 stage 175ms → 3.8ms，
   整步 499ms → 276ms。
2. **删掉每层「还槽位」**：小卡按「装不下整步」判断，每层把整层专家扔回池子，
   每 token 重读 4.5GB。
3. **槽位池覆盖式分配**：空槽 LIFO + 环形游标，删掉每层遍历 1359 个槽位
   找 victim 的 Python 循环。
4. **槽位表由池子自维护**：以前散在 `moe.py` 里，漏一处就是「kernel 读到
   别人的权重」这种静默错误。
5. **滚动预取**：算第 k 层时搬 k+1 层的专家进槽位（`urgent=False` 只填空槽）。

## 可调的旋钮

- `TI_SLOTS`：槽位数（默认由 planner 按真实显存算）
- `TI_TOP_K` / `tier.expert_topk`：路由 top-k（默认 checkpoint 的 6；
  降到 4 能省 33% 的专家搬运，代价是质量）。这是「计算换 IO」的真实旋钮，
  但**没有实测过质量损失**，不要想当然地用。
- `TI_MAX_BATCH` / `max_slots`：并发数（默认由 `plan_slots` 按显存和上下文算）
- `TI_WARM`：空闲预热（默认开；会在推理时让路）
