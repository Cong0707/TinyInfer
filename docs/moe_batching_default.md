# MoE 分批：默认值改为按槽位容量自适应（2026-11-08 13:03）

## 改动

`TI_MOE_BATCH` 不再默认 3，而是**由槽位池容量推导**：

```python
need = rows * topk
if cap <= 0 or cap >= need:
    bs = rows          # 装得下：整批，不分批
else:
    bs = max(1, cap // topk)   # 装不下：按容量切
```

## 依据

1. **分批路径有多行 NaN bug**（docs/nan_batch_verdict.md）：NaN 位置随批次
   大小移动，加任何 hook 就消失，是数据竞争。
2. **不分批时数值全部正确**：N=8/11/12/16/20 五个长度都 `bad=[]`。
3. **L20 根本不需要分批**：1359 个槽位 vs 66 个请求（11 行 x 6）。

## 实测验证（8GB 卡，14 槽位）

```
TI_SLOTS=14:
  N= 8  bad=[]      8x6=48 > 14 -> 分批上限 14//6=2，恰好避开 bug
  N=11  bad=[10]    11x6=66 > 14 -> 分批上限 2，仍然命中 bug
  N=16  bad=[]      16x6=96 > 14 -> 分批上限 2
```

**8GB 卡上仍然会命中 bug**（N=11 就是），因为池子只有 14 个槽位，必须分批。
这是物理约束下的已知缺陷，不是新引入的。

## L20 上的行为（推算，未验证）

```
1359 >= 66  ->  _moe_bs = rows  ->  整批，不分批  ->  数值正确
```

而且整批还更快（少 3 次 kernel launch 和 3 次同步）。

## 本机无法验证 L20 的行为

试着用 `TI_SLOTS=600` 模拟 L20 的容量，但 600 x 18.8MB = 11GB > 8GB 显存，
直接 OOM，拿不到结果。**这条只能在 L20 上验证。**

## 遗留

分批路径的竞争未修。它影响：8GB 卡上超过 2 行的 prefill。
修它需要 `compute-sanitizer --tool memcheck` 这类工具，打印法无效。
