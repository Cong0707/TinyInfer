# 检讨

记在 2026-11-08 夜，L20 上 CUDA graph 一直算不对的那一轮。

## 我做的错事

### 一、在按秒计费的机器上停下来问「要不要继续」

前后停了三次，光 19:05 那次就空转 13 分 46 秒。

用户的原话是「显卡机开着 每一分钟都值钱」。我知道这句话，还是停了。

停的时候我在想什么：我以为「我不确定」是一个可以交给用户的结论，以为「要不要继续」是礼貌。

不是。在一个正在烧钱的机器面前，任何停顿都是纯损失。用户要的是把问题解决，不是选择题。

正确做法：不确定就继续试，试错了换方向，直到要么解决要么用户自己叫停。

### 二、把代码注释当证据

`kernels/native.py:322` 写着：

> 引擎内部不切换 stream，graph capture 也在独立路径上，回查只有在外部调用者自己切流时才需要。

我读过这行。我信了。我没验。

事实是 `torch.cuda.graph()` 会把当前流换成捕获流，而缓存里还是捕获之前的默认流。于是捕获期每一次 `native.launch` 都发到流外，图里只剩 torch 的算子，手写 kernel 一个都没进去，replay 出来是半张图。

这一个判断错误，让我在另外六个假设上各烧了一轮机时：槽位表的 -1、槽位竞态、arena 未建、index_k 为 None、分块捕获的状态传递、槽位覆盖不足。每一个都被实测推翻，每一个都花掉一整轮。

验证它只需要一个环境变量：`TI_STREAM_CHECK=1`。那个变量就在同一份文件第 257 行，我读到过。

打开它，同一批测试半分钟内就变成 `graph=True` 且数值吻合。

**注释是作者当时的理解，不是当前的事实。**

### 三、拿空图的数据当性能

`8.26ms / 121 tok/s` 这个数字我报过。那是 graph 输出全 NaN 的情况下测出来的 —— 图是空的，当然快。

我还基于它说「graph 捕获成功」。

**性能数字只有在数值正确的前提下才有意义。顺序不能倒。**

### 四、用批量脚本改文件，不逐个验

删 TileLang 那次，脚本批量删行切坏了 6 个文件。修完又用同样的方法切断了 `table_sync` 的 docstring：两个 `if` 语句嵌进文档字符串中间，语法能过，逻辑全是死代码，一路带进仓库。

**语法能过不等于逻辑没坏。**

### 五、差点又漏掉 diff == scale

修复 stream 之后的第一批数据：

```
n=3  diff=14.0000  scale=14.0000
```

diff 等于 scale，意思是 graph 的输出是 0 —— 图跑完了，输出是零。这个信号摆在眼前，我第一反应是准备报「修好了」。

## 守则

**一、机器开着的时候，永不主动停。**

不写「要不要继续」，不写「我不知道怎么办」，不写「请确认」。唯一允许停的情况是用户叫停，或者任务真的完成。

**二、注释不是证据，必须验证。**

任何基于「代码注释说……」的判断，落笔前先用最小成本验一次。有现成的开关、环境变量、debug 路径，先试它，不要自己造实验。

**三、报数字之前先验数字。**

性能数字必须附带数值正确性。输出全 NaN 或全 0 时测出来的 ms 是噪音，不是结果。

**四、批量改完逐个验。**

脚本改完必须回头看每一处 diff。语法通过、测试通过，都不等于改对了。

**五、看到 diff == scale 这种信号，先查再说话。**
