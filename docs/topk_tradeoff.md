# topk 4 vs 6：8GB 卡上 27% 的提速（2026-11-08 14:37，实测）

## 数据（8 层模型，decode 单步）

```
topk=6   273 ms/step   argmax=82050   finite=True
topk=4   200 ms/step   argmax=82050   finite=True
```

**耗时降低 27%，本步 argmax 相同。**

## 为什么有效

`n_exp` 从 48 降到 32（8 行时），专家搬运量减少 33%。
而 8GB 卡上 decode 的耗时几乎全在搬专家（`docs/bottleneck_8gb.md`），
所以搬得少就快得直接。

实测 200/273 = 0.73，与「搬 2/3 的量」吻合（理论 0.67，多出的 6% 是计算部分没变）。

## 代价

**质量。** topk 从 6 降到 4 意味着每个 token 少看 2 个专家，
模型的表达力下降。这一步 argmax 相同不能说明整体质量不变 ——
长文本生成、复杂推理上会有退化。

**我没有测质量**，也不打算凭一次 argmax 相同就说「质量没损失」。

## 这是个「用户可选的旋钮」，不是默认值

```powershell
$env:TI_TOP_K = "4"     # 或 tier.expert_topk
```

`tiers.py` 里 `expert_topk` 字段的注释写着：

> `0 = checkpoint top-k (6); lower values trade quality for IO`

**这个注释是准确的**：它在拿质量换 IO。

## 对目标场景的意义

L20 上稳态零搬运，**topk 降低不会带来提速**（因为本来就不搬），
只会损失质量。所以：

| 机器 | topk=4 的收益 | 建议 |
| --- | --- | --- |
| 8GB（100% miss）| **27% 提速** | 想快可以开 |
| L20（零搬运）| 几乎为零 | 不要开 |

**这正是「引擎自适应」该做的事**：在搬运是瓶颈的机器上可以降 topk，
在槽位充足的机器上保持 topk=6。而不是无条件取一个值。

## 待办

- 如果要做成自适应的，判据是「槽位是否能覆盖 n_layers * topk」。
  能覆盖 -> topk=6；不能 -> 可以降到能覆盖的最大值。
- 但**降 topk 损失质量**，不能自动做。应该是用户显式选择，
  引擎只负责报告「当前配置下 topk=6 会有多少 % 的 miss」。
