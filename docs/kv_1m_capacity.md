# 1M 上下文的压缩 KV：7.25GB/条（2026-11-08 14:42，与实测核对）

## 修正一个我自己的算错

第一次按「每个元素 1 字节」算，得到 **14.50 GB**，然后以为代码注释里的
「6.92GB（实测）」是错的。**错的是我** —— 漏了压缩 latent 是 **fp4**（0.5 字节）。

```
fp8 (1.0 B)  1M -> 14.50 GB      <- 我一开始的错算
fp4 (0.5 B)  1M ->  7.25 GB      <- 正确
代码注释实测:     6.92 GB        <- 吻合（差 5% 是几何增长的取整）
```

## 逐层构成

| ratio=2 的层（18 层）| 每层 256MB | 合计 4.5GB |
| ratio=1 的层（20 层）| 每层 512MB | 合计 10.0GB |

（fp8 口径；fp4 减半。）

## L20 上能跑几条 1M 会话

| 可用显存 | 1M 会话数 |
| --- | --- |
| 36GB（扣 8GB 给层权重/缓冲）| **4 条** |
| 40GB | **5 条** |

这与之前 `plan_slots()` 算出的「1M -> 5 条」一致（那个用 44-4=40GB）。

## 这条信息的价值

1. **确认 1M 上下文在 L20 上可行**，不是理论值。
2. **每多一条 1M 会话要 7.25GB 显存** —— 这是 L20 上并发的硬天花板。
   想跑 10 条 1M 会话需要 72.5GB，得 80GB 的卡。
3. 几何增长（1024 -> 翻倍）不会浪费：因为 1M 正好是 2 的幂，
   `cap` 最后一次翻倍恰好等于需求（`probe_kvcap.py` 验证浪费 = 0）。

## 相关的已知限制

- 增长只在 prefill 阶段发生（`s > 1`），decode 阶段不再增长 ——
  这是为 CUDA graph 的地址固定性做的妥协
- 扩容时会 `torch.zeros` 新开一块 + 拷贝旧数据，1M 时峰值是 **2 倍**
  （新旧两块同时在），显存紧张时可能 OOM
