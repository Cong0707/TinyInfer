# 更精确的机制：装不下的专家被跳过，kernel 仍按它们算（2026-11-08 14:23）

## 上一轮的结论要修正

上一轮我说「兜底抢走了正在计算的层的槽位」。实测：

```
urgent_evictions: 0 -> 0     <- 兜底压根没触发
slots=14  loads=14  hits=0
```

**`"any"` 兜底没被调用。** 真正发生的是：

## 真正的机制

`stage()` 里：

```python
idx = self._reserve_locked((layer, e), protect_urgent=True)
if idx is None:
    continue      # <- 拿不到槽位就跳过，不搬
```

8 行 batch 要 48 个槽位，池子 14 个 —— 前 14 个搬进来，剩 34 个 `continue` 掉了。

而 `sids`（GPU 侧槽位表）里那 34 个专家的条目**仍是旧值或 -1**，
kernel 拿它去 `arena + slot*blob_bytes + off` 寻址 —— 读到的是别人的字节。

所以 `loads=14` 的意思是「只搬了 14 个」，而 `n_exp=48` 的 kernel 要用 48 个。

## 这解释了一切

- 为什么 20% 的相对误差：14/48 的专家是对的，其余 34 个读错了
- 为什么单行（n_exp=6）正常：6 < 14，全部装得下
- 为什么 `bytes_equal=True`：搬进来的那些字节是对的

## 这是设计缺陷，不是纯物理限制

槽位不够是物理事实，但**引擎可以选择在装不下时拒绝计算或分批**，
而不是静默地拿错数据算出结果。

现在的行为是「静默错误」—— 最糟的一类。

## 正确的修法（两个选项）

### A. 装不下就分批（推荐）

在 `_forward_gpu_only` 的入口检查 `n_exp <= slots`，不满足就按 `slots // topk` 行一组
分批。这样每批都能装满，不会静默错。

代价：多几次 kernel launch 和同步。

### B. 装不下就明确失败

抛 `RuntimeError("layer N needs 48 slots, pool has 14")`。至少不会算错。

对生产环境，A 更合适（慢但正确）；B 会让 8GB 卡完全不可用。

## 已做的改动

`urgent_evictions` 计数器加上了（现在恒为 0，但保留了 —— 它是「兜底抢槽」
的探测器，未来槽位紧张时有用）。

## 下一步

这正好和之前「默认不分批」的改动衔接 —— 那时候是因为 3 行太保守，
