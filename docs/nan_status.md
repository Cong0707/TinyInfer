# NaN 追查状态：需要更系统的工具（2026-11-08 12:54）

## 已经非常确定的事

1. **NaN 只在多行 prefill（`xf.size(0) > 3`）时出现**，单行 decode 不受影响。
2. **NaN 的位置随 MoE 批次大小移动**：

| 批次 | 切分 | NaN |
| --- | --- | --- |
| 2 | 2x5+1 | 无 |
| 3 | 3+3+3+2 | [10] |
| 4 | 4+4+3 | [8,9] |
| 6 | 6+5 | [10] |
| 8 | 8+3 | 无 |
| 11 | 11 | 无 |

3. **加任何 hook（哪怕只读 buffer 形状）就正常**。
   这意味着极度时序敏感 —— 打印引入的同步改变了结果。

## 已排除的假设

| 假设 | 验证 | 结果 |
| --- | --- | --- |
| `_o.clone()` 早于 synchronize | 改成先同步后克隆 | NaN 不变 |
| 槽位覆盖竞态 | 加 `_slot_idle` 检查 | NaN 不变（已回退）|
| 层间竞态 | 逐层 synchronize | NaN 不变 |
| `compress_kv` 未初始化 | 逐组检查 | 全部 finite |
| 数值放大（rms_norm/MoE）| 逐层逐位置 | 只有特定行异常，不是全体 |
| `window_idxs` 越界 | 索引检查 | 正常 |

## 当前最可信的判断

这是 **MoE 多行路径里某个 GPU buffer 的真实数据竞争**，而且：

- 只在多行时出现（单行路径不经过分批）
- 对批次划分敏感（说明与 buffer 大小/复用有关）
- 对任何额外同步敏感（hook 就能掩盖）

涉及的共享 buffer：`_gpu_y_buf`、`_sids_buf`、`_aq_buf`、`_ascb`、`_scratch`，
以及 `_launch_keep`（driver-API kernel 不认 Python 引用）。

## 为什么应该换个思路

继续用「加打印看数值」的方法追这个竞态，成本已经很高（十几轮），
而且**每次加打印都会改变结果**，本质上没法用这种方法定位。

正确做法应该是：**让分批之间完全不共享 buffer** —— 每批分配自己的输出 buffer
并立即拷出，而不是复用 `_gpu_y_buf`。这个改动同时也能验证假设：
如果 NaN 消失，就确认是 buffer 复用。

## 下一步（下一轮做）

在 `_forward_gpu_only` 的递归分支里，给每批一份独立的输出缓冲：

```python
_o = self._forward_gpu_only(...)
_outs.append(_o.clone())   # 已有
# 关键：不依赖 _gpu_y_buf 跨批复用，改为每批独立
```

或者更彻底：递归分支里把 `self._gpu_y_buf` 临时置 None，强制每批新建。
代价是多几次分配（每批 5120*rows*2 字节，可接受）。
